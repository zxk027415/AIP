# 需求文档：光伏时序故障诊断（pv-fault-timeseries-diagnosis）

## 引言（Introduction）

本 spec 是从 `pv-fault-label-segment-redesign`（逐点标签重构）中**独立拆分**出来的时序建模路线。逐点标签重构那条线走的是「把一段窗口聚合成统计特征 + 随机森林分类」，它的固有局限是**聚合会丢掉时间顺序**——把一段功率曲线压成均值/方差/分位数后，「先平稳后骤降」和「先骤降后恢复」这两种截然不同的故障形态会算出几乎一样的特征。

本 spec 走另一条技术路线：**直接在原始时序上建模，不做人工统计特征聚合**，用滑动窗口切样本、序列模型（CNN-LSTM / Transformer / 专用时序分类算法）学习故障的时间形态。目标是把「时序形态」这个被 RF 路线丢弃的信息重新利用起来。

两条线的关系：**并行、互补、对比精度**，不是替代关系。逐点标签重构负责标签治理与 RF 路线；本 spec 负责时序形态建模。两者共用同一套逐点标签存储（`point_labels` / `label_ops`）作为标签事实来源，区别只在「标签之后怎么切样本、用什么模型」。

本阶段交付物仅为本需求文档（含调研结论）。不修改任何生产代码，不预设实现结构。

## 为什么单独拆出来（与逐点标签 spec 的边界）

| 维度 | 逐点标签 spec（RF 路线） | 本 spec（时序路线） |
|---|---|---|
| 样本切分 | `by_day` / `by_day_night`（按天/白天夜间） | 滑动窗口（固定长度 + 步长） |
| 特征 | 窗口聚合统计特征（均值/方差/分位数/自相关…） | 原始序列直接输入，模型自学特征 |
| 模型 | `RandomForestClassifier` | CNN-LSTM / Transformer / ROCKET / InceptionTime |
| 时间顺序 | 聚合后丢失（差分/自相关部分弥补） | 完整保留，是建模的核心 |
| 跨天建模 | 不支持（按天自洽） | 天然支持（窗口长度可跨天） |
| 训练/预测一致性 | 按天，训练预测口径一致 | 滑动窗口，训练预测口径一致 |
| 算子约束 | 零新增算子（硬约束） | **不受该约束**，可新增时序算子/模型 |

关键澄清：原 `pv-fault-label-segment-redesign` 里一度设计过 `by_label_run`（跨天但仍走 RF 聚合）切分模式。它是个尴尬的中间态——既想跨天、又用聚合特征，且预测时无标签只能退化为按天，造成训练/预测特征窗口长度不一致。该模式已从逐点标签 spec 移出（见其决策 K8），跨天/时序建模的诉求由本 spec 用真正的序列模型承接。

## 调研结论（Research Summary）

以下为时序故障诊断领域主流做法的调研,内容为合规改写,附来源。作为本 spec 方案选型的依据。

### 1. 输入切分：滑动窗口是标准做法

时序故障诊断普遍用**滑动窗口**把长序列切成固定长度样本,由「窗口长度 + 步长」两个参数控制,而不是按「天」或「标签段」切。这正对应本 spec「抛开天的概念、按一段时序建模」的诉求。

- [跨机器故障诊断 ResFCN 迁移学习用滑动窗口分段](https://www.mdpi.com/1424-8220/25/4/1189/xml)（2025）
- [PCB 蚀刻监测用固定长度窗口做局部时序特征提取](https://www.mdpi.com/2227-7390/13/17/2804)（2025）
- [CNN-LSTM 复杂系统故障诊断:滑动窗口整合特征与时延信息](https://link.springer.com/article/10.1007/s10462-021-09993-z)

### 2. 主流模型：端到端吃原始序列,不做人工统计特征

- **CNN-LSTM / CNN-BiLSTM** 是光伏领域最常见组合:CNN 提局部形态、LSTM 抓时间依赖。[光伏 DC 子模块开路故障 CNN-LSTM](https://www.mdpi.com/2079-9292/14/6/1205/xml)（2025）、[多尺度 CNN-BiLSTM + 时间注意力](https://www.mdpi.com/1424-8220/25/14/4474)（2025）。
- **Transformer / CNN 处理原始时序表现最好**:[光伏异常检测数据表示方法对比研究](https://www.mdpi.com/2227-7390/14/3/501/xml)（2026）结论是能处理原始时序的 CNN 和 Transformer 精度最高。
- **两阶段混合(可复用现有 RF)**:[LSTM 自编码器无监督异常检测 + 随机森林故障分类](https://www.mdpi.com/2673-4117/6/10/254)（2025）——这个架构能把现有 RF 当第二阶段,只在前面加时序特征提取,迁移成本低。
- **专用 TSC 算法**:时序分类(Time Series Classification)是成熟子领域,有 ROCKET、InceptionTime 等专门算法,通常比通用深度网络更轻、基线更强。

### 3. 对本 spec 的选型建议

- **基线先行**:先上轻量的 ROCKET / InceptionTime 做基线(训练快、不需要调很多超参),验证「时序形态是否真能提升精度」这个假设,再决定是否投入 CNN-LSTM。
- **可复用 RF**:若走两阶段(时序特征提取 + RF 分类),能最大程度复用逐点标签 spec 已有的 RF 评估链路,与其做精度对比也更公平(只换特征提取、不换分类器)。
- **内容合规声明**:上述结论均为对公开文献的改写与归纳,非逐字引用。

## 需求（Requirements，草案）

> 本 spec 尚处调研+需求草案阶段,以下为初步需求,细化留待设计阶段。

### 需求 1：滑动窗口切分

**User Story:** 作为算法工程师,我希望把时序数据按可配置的滑动窗口切成样本,以便时序模型学习跨天的故障形态。

#### 验收标准

1. THE 时序切分器 SHALL 提供 `window_length`（窗口长度,如 288 点=1 天、或更长）与 `stride`（步长）两个参数,把每个设备的连续时序切成等长窗口样本。
2. THE 时序切分器 SHALL 支持窗口跨自然日,不强制按天断开。
3. WHERE 一个窗口内出现多个标签,THE 时序切分器 SHALL 按可配置策略处理(如取众数 + 记录纯度、或在标签变化处对齐窗口边界),该策略在设计阶段确定。
4. THE 时序切分器 SHALL 从逐点标签 spec 的 `point_labels` 读取标签,不自建标签存储(共用同一标签事实来源)。
5. THE 时序切分器 SHALL 保证训练与预测使用相同的 `window_length` / `stride`,策略随模型持久化。

### 需求 2：序列模型选型与基线

**User Story:** 作为算法负责人,我希望先有一个轻量的时序分类基线,以便验证时序形态建模是否真的比 RF 聚合特征更准,再决定投入产出。

#### 验收标准

1. THE 本 spec SHALL 先实现一个轻量 TSC 基线(ROCKET 或 InceptionTime),不直接上重型 CNN-LSTM。
2. THE 基线 SHALL 在与逐点标签 RF 路线相同的数据与评估口径(同 `n_repeats` / `test_ratio` / 随机种子)下评估,产出可对比的精度指标。
3. IF 时序基线精度显著优于 RF 路线,THEN 才评估是否投入 CNN-LSTM / Transformer 等重型模型。
4. THE 时序路线的模型 SHALL 与逐点标签 spec 的 RF 模型互为备选(对应逐点标签 spec 需求 23 的双路径对比,本 spec 是其中一条候选路径)。

### 需求 3：与逐点标签 spec 的集成边界

**User Story:** 作为平台维护者,我希望时序路线和 RF 路线清晰解耦,以便两条线独立演进、互不阻塞。

#### 验收标准

1. THE 本 spec SHALL 复用 `point_labels` / `label_ops` 作为标签唯一事实来源,不新建标签表。
2. THE 本 spec **不受**逐点标签 spec 的「零新增算子」硬约束——时序建模允许新增时序切分与模型算子。
3. THE 本 spec SHALL 复用逐点标签 spec 的对比评估骨架(`split_mode_compare.py` 扩展),作为双路径对比的一条路径接入。
4. THE 两条线的生产切换 SHALL 通过逐点标签 spec 需求 23 的 `production_path` / `fallback_path` 双指针统一管理,本 spec 的时序模型作为其中一个可选 path。
