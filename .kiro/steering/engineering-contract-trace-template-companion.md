# 《工程改动教学模板》配套说明（入门向）

正文模板文件：`docs_zxk/ENGINEERING_CONTRACT_TRACE_TEMPLATE.md`。下面按**章节**说明每块在学什么、填什么；**英文字段**后附 **中文含义**。

## §0 使用说明

- **一次改动一份**：避免多需求混写，否则字段链会乱。
- **先事实后观点**：先填文件路径、字段名、接口；再写「为什么这样设计」。

## §1 改动摘要（What Changed）

- **需求背景**：业务目标（business goal）— **为什么要做**；非功能目标 — **性能 / 兼容 / 安全**等。
- **变更范围**：列出 **frontend（前端）** / **backend（后端）** / **operator（算子）** / **config（配置）** 文件，方便 code review 与学习复盘。
- **行为变化**：**改前 vs 改后** — 用户看得见的行为，用来验收。

## §2 字段流转链（Data Flow Trace）

核心：**Data flow trace（数据流追踪）** — 同一个「业务语义」在不同层往往有不同 **field name（字段名）**。

- **§2.1 字段总览表**：一行对应一个语义，列包括 **UI 字段**、**HTTP 字段**、**API 内变量**、**global_config（全局配置）键**、**算子读取点**、**最终影响**。目标是 **field name 可搜索、可追踪**。
- **§2.2 逐层**：A UI → B HTTP → C API Handler → D 执行上下文注入 → E 算子消费 → F 输出回显。每层至少写 **1 个输入字段**、**1 个输出字段**。

## §3 数据契约（Data Contract）

- **API 契约**：**Request schema（请求体形状）** / **Response schema（响应体形状）** — 类型、可选、默认值；可用 JSON 示例。
- **global_config 契约**：谁 **produce（写入）**、谁 **consume（读取）**、默认值、是否必填。
- **算子 I/O**：**输入契约** / **输出契约**；临时字段写清 **lifecycle（生命周期）**（谁创建、谁消费、何时清理），避免「幽灵字段」。

## §4 设计权衡（Why This Design）

- **复用性**：专属行为是否默认开启？**开关字段**是什么？为何不伤及其他场景。
- **向后兼容**：**旧请求（legacy request）** 是否仍有效；**未传新字段** 时行为是否与旧版一致。
- **风险与防护**：**触发条件（trigger）** + **防护措施（mitigation）**。

## §5 验证清单（Validation）

- **功能**：UI → 请求 → 注入 → 算子 → 页面。
- **兼容**：不传新字段、非本模式路径是否仍正常。
- **工程**：**tsc** / **lint** / 后端语法检查等（按项目实际命令）。

## §6 学习闭环（Learning Loop）

- **关键词**：本次最多 3 个术语，强制浓缩记忆。
- **5 分钟复盘**：改名在哪一层？默认值？哪个 `if` 决定行为？
- **可复用结论**：下次类似需求可直接套用的句式或模式。

## §8 排错速查（Debug）

模板附录：**UI 无字段 → 看 Network（网络请求）**；**后端有值算子无效 → 看是否进 global_config**；**config 有值仍无效 → 看算子分支与拼写**；**疑似泄漏 → 看掩码与真值列**。

---

**对 AI 的期望**：当用户正在填写或讨论该模板时，主动按 §2 帮用户补全「一层一层」的字段名对照，并指出 **default（默认值）** 与 **branch（分支）**；避免只改代码不留下可追溯记录。
