### 前后端怎么通信

```
浏览器 (React)  ──HTTP /api/*──>  Vite 开发服务器  ──代理转发──>  FastAPI (Python)
   :3001                          VITE_API_PROXY_TARGET          :8081
```

- 端口由 `aip.ps1` 决定：dev 模式后端 8081（带 reload）、前端 3001。
- 前端不硬编码后端端口，`aip.ps1` 把 `VITE_API_PROXY_TARGET` 注进前端进程。
- 后端 CORS 白名单在 `main.py`，改端口时要一起改。

**这个仓库的一个特点：持久化真源大量是 JSON 文件，不是数据库。** `data/` 下的 JSON 就是业务真相，所以：
- 不要随手删 `data/` 里的东西，那不是缓存。
- 并发写同一个 JSON 会互相覆盖——`ScopedRegistryStore.update()` 本轮才改成原子 read-merge-write。
- 单体 JSON 长大就会拖慢一切，`outcomes.json` 已经 132 MB（见 2.7 第 3 项）。

2. **第 29-39 行有一段全进程猴子补丁，而且整条算子链都靠它活着。别删。**

   ```python

   def _patched_date_range(*args, **kwargs):
       if "closed" in kwargs:
           closed_val = kwargs.pop("closed")
           ...  # 翻译成 inclusive=
   ```

   |---|---|
   | `backend-service/features/engine.py` | 172、187、230、245、254、263（6 处） |
   | `backend-service/models_pkg/wrapper.py` | 145（1 处） |

   实测裸调用会报：

   ```
   TypeError: DatetimeArray._generate_range() got an unexpected keyword argument 'closed'
   ```

   `main.py` import `api/load_forecast.py` 时补丁生效，所以整个后端进程里这 7 处才不炸。**这是一条隐式的、跨模块的进程级依赖**：清理链 A 的时候如果顺手把补丁删了，链 B 的算子会全线崩，而且报错栈里看不到 `load_forecast.py`，很难定位。

### 2.4 治理硬门（fail-closed，别绕）

这些门是有意设计的，绕过它们会污染候选池和血缘链：

1. **`register_candidate` 要求 `bound_snapshot_id`（绑定的冻结快照标识）** — 没有就报 `candidate_snapshot_missing`。
2. **快照需要 admission 事件才能冻结** — 唯一产出入口是 `review_service.complete_and_admit()`。
3. **`pv_point` 冻结排除 `device_day` 粒度** — 原因码 `whole_day_box_not_point_truth`。
4. **`run_mode=experiment` / validation / sandbox 恒非可治理** — 只有 persisted training workflow + `run_mode=training` + 非 sandbox 才可能 `governance_eligible=true`。
5. **跨路径挂载 fail-closed** — `assert_entry_mountable()` 在服务端拦截，不信客户端传的 origin 字段。
6. **Project Promote 无 `force` 旁路** — 必须同 scope 候选、`passed=true` verification、匹配 registry version、operator/reason/idempotency key；它只改 project registry。
7. **`experiment_only` 当前不是硬门** — preflight 的该字段只在 UI 提示和 execution 审计中保存；runner 只硬拦 `overall=blocked`，仍可能允许 training 模式并计算可治理资格。这是 P0 治理缺口，不能在文档中当成已生效门禁。

**⚠️ 最容易误解的一条：项目 registry ≠ slot registry。**

项目 Promote 写的是**项目** registry；定时调度、算法部署和回放读的是**slot** registry。两套介质分别是：

- project governance：`backend-service/data/slot_governance/projects/<project_id>/<slot>/` — 项目 registry、候选、复验、Promote 审计；
- slot governance：`backend-service/data/slot_governance/<slot>/` — 全局 Champion/Challenger/rolling、slot candidate、slot 复验和 Promote 审计；
- 项目 execution/review/snapshot/workflow：`backend-service/data/pv_projects/projects/<project_id>/<slot>/`；
- 项目数据资产/版本：`backend-service/data/slot_datasets/projects/<project_id>/`。

**在项目里 Promote 不会改变生产回放模型。** 要改变调度实际用模，必须走独立 slot governance。

**⚠️ 项目 runner 是可审计执行账本，不是算法执行器。** `ScopedWorkflowRunner.start_execution()` 只校验 scope/工作流/模式/preflight，然后登记 `status=running`、绑定版本/快照和 pending 节点时间线；不会调用 enhanced workflow 或算子。`finalize()` 也由外部执行器/调用方回写终态、`node_results` 和 `model_artifact_ref`。只有成功、可治理且拿到工件时，才自动登记 project candidate。

**Project candidate → slot candidate 领域桥已经有代码，但不是强事务。** `main.py` 启动时安装 `PvFaultCandidateBridge`：项目 finalize 后先镜像 execution 到统一历史，再登记 slot `mc-*` candidate；候选只进池，不自动成为 Challenger。只有 project verification 被完成为 passed 后，桥才把对应 slot candidate 写成 slot Challenger；桥失败不会回滚 project candidate，必须检查 `candidate.domain_sync`。

**Project verification 当前没有自动 compare。** `start_verification()` 只写 pending 和 `comparison_id`；`complete_verification(passed=...)` 的 passed 由调用方提交，当前 caller-passed 记录不能替代有多窗指标的科学复验。

## 3. operation_skill（负荷预测运营闭环 Agent Skill）

### 3.1 定位

一个**自包含的 Agent Skill**：负荷预测精度劣化时，自动跑「检测 → 证据采集 → 根因分析(RCA) → 策略评估 → 执行恢复 → 验证 → 专家经验(CoE)沉淀」闭环，最后产出一张 HTML 看板。

**依赖极轻**：`requirements.txt` 只有 `numpy>=1.24.0`、`pandas>=2.0.0`、`xgboost>=1.7.0`。不依赖后端、不依赖数据库（默认走本地缓存）。

**位置：`local_project/load_forecast_refactored/operation_skill/`**（已跟踪、唯一真源）。原来的 `local_project/operation_skill/` 第二份副本经 41 个文件 SHA-256 核对完全相同，已移入可恢复归档。

**Skill 契约**：`SKILL.md` 的 front-matter 声明 `name: algorithm-lifecycle-ops`、`version: 3.0.0`，触发词包括「精度劣化」「数据缺失」「根因分析」「RCA」「运营闭环」「策略恢复」「负荷预测」等。

### 3.2 三入口三阶段

设计是**脚本跑数据、Agent 做推理**，中间用 JSON 文件交接。

```
run_collect.py  →  rca_input.json  →  [Agent 推理]  →  rca_decision.json  →  run_resume.py  →  HTML 报告
   (脚本)                                (人/LLM)                              (脚本)
```

#### 阶段 1：collect — 证据采集

**入口**：`scripts/run_collect.py`

`--target-day` — 事故日（D+1，预测目标日）。**默认 `2026-05-24`**，缺失日是它的 D-1。

**内部五步**（全部 XGBoost 实算，不是 mock）：
1. 从缓存/数据库拉真实数据 → `load_real_dataset()`
2. 基线预测（真·gap 一天，lag 指向 D-1）→ 基线精度

#### 阶段 2：reasoning — Agent 推理（无脚本）

#### 阶段 3：resume — 执行恢复 + 验证

**入口**：`scripts/run_resume.py`

**五条校验（`run_resume.py` 第 128-143 行）**，任一不过就降级到规则兜底 `_fallback_rca()`（第 62 行），并记 `degrade_reason`（降级原因）：

### 3.4 精度口径

`scripts/core/metrics.py`：

```python
def clamp(value, low=0.0, high=100.0):        # L8
    return max(low, min(high, value))          # L9

mape = sum(abs(t - p) / max(abs(t), 1e-8) for t, p in zip(y_true, y_pred)) / len(y_true)  # L16
accuracy = clamp((1.0 - mape) * 100.0)         # L17
```

与 `SKILL.md` Rules 第 6 条「Accuracy = (1 − MAPE) × 100%」一致。

#### ⚠️ 这里有一个会静默出满分的 bug，实测结果如下

| 输入 | 返回 |
|---|---|
| `y_true` 全是 NaN | `{"accuracy": 100.0, "mape": nan, "status": "ok"}` |
| `y_true` 里**只有 1 个** NaN（4 个点） | `{"accuracy": 100.0, "mape": nan, "status": "ok"}` |
| 正常数据 | `{"accuracy": 94.17, "mape": 0.058333, "status": "ok"}` |

**只要真值序列里出现一个 NaN，整段精度就变成满分 100，而且 `status` 还是 `ok`。**

机理在 `clamp` 那行：`min(100.0, nan)` 因为 `nan < 100.0` 恒为 `False` 而返回 `100.0`，再 `max(0.0, 100.0)` = `100.0`。NaN 被 clamp 悄悄吃掉了。

**为什么这条特别要紧**：这个 skill 的全部业务前提就是「检测负荷数据缺失导致的精度劣化」，而缺失数据恰恰就是 NaN。也就是说**这个 bug 正好落在 skill 的核心场景上**——如果哪天真值侧（不只是特征侧）出现缺失，系统会报 100 分「一切正常」，而不是报警。

复现：

```powershell
cd local_project\load_forecast_refactored\operation_skill
conda run -n cp_web python -c "import sys; sys.path.insert(0,'.'); from scripts.core.metrics import evaluate_accuracy; print(evaluate_accuracy([1.0,float('nan'),3.0,4.0],[1.0,2.0,3.0,4.0]))"
```

修法：在 L16 之前加 NaN 校验，命中就返回 `err(ErrorCode.METRIC_ERROR, ...)`；或者在 `clamp` 里显式判 `math.isnan`。**改完必须补测试**，这是 3.9 里建议的第一条。

#### 10.1.1 专用训练页怎么进入

#### 10.1.2 训练页每个区域是什么意思

| 区域 | 你看到什么 | 实际作用 |
|---|---|---|
| 场景选择 | DI/D/WI/W/MI/M 六张卡 | 选择日内、日前、周内、周前、月内、月前预测；加载失败可重试 |
| 参数配置 | 场景、预测步长、粒度、分段建模、起始时刻 | 组成 `POST /api/load-forecast/train` 请求 |
| 高级选项 | CSV 路径、parent_id、child_id | 留空用后端默认；路径必须填仓库相对路径 |
| 训练进度 | 数据获取→异常检测→特征工程→模型训练 | 每 2 秒轮询任务状态，不等于真实流式推送 |
| 日志控制台 | 深色终端日志 | 后端日志优先；看失败原因最重要的地方 |
| 训练结果 | Model ID、耗时、步骤图 | 该 model 只存在当前后端进程内存，重启失效 |
| 回测 | 快速回测/日期范围/日统计图 | 另起回测任务；**不消费刚训练的 model_id** |
| 训练历史 | 本次浏览器会话内的记录 | 刷新页面就丢，只能回填参数，不能恢复日志 |
| 快速操作 | 重置状态/刷新场景 | 重置不删除后端任务，也不清会话历史 |

参数解释：

- `task_type` — 场景，必填；初次建议选 D（日前）。
- `forecast_horizon` — 向未来预测天数，默认 1。
- `time_granularity` — 15/30/60 分钟，默认 15min。
- `separate_modeling` — 工作日/节假日分开训练，默认关；HTTP 发送字符串 `true/false`。
- `forecast_start_time` — 每日预测起点，默认 00:15。
- `csv_path` — 相对路径；留空默认 `backend-service/datasets/load_true_weihai_260415.csv`。
- `parent_id/child_id` — 父级和预测对象；留空后端使用默认园区/设备。

#### 10.1.3 可照做的训练与回测步骤

1. 等六张场景卡加载完成；失败点“重试”。
2. 点“日前预测（D）”。
3. 初次验证保留步长 1、15 分钟、分段建模关闭、00:15。
4. 无自有数据时高级选项全留空；有数据填**相对仓库路径**。
5. 点“开始训练”。表单会禁用，防止重复提交。
6. 看四步进度和日志。不要刷新页面，否则前端状态/历史丢失，但后端线程可能仍在跑。
7. 成功后复制 Model ID；失败看红色卡和日志，再点“重新训练”。
8. 点“快速回测”跑默认日期范围，或选起止日期点“自定义回测”。
9. 看成功/跳过/失败天数和每日预测值均值/最大/最小、点数。这里没有 actual 真值曲线，也不计算 MAPE。
10. 如果回测一直转圈，页面没有取消按钮；查后端任务状态和日志，必要时重启服务。

**最重要边界**：训练页的 `model_id` 不进入回测请求、不进入部署 registry，也没有前端 predict 按钮。它是演示/临时训练链，不是生产发布链。

#### 10.1.4 精度运营页怎么读

页面从上到下：

1. **四格总览**：当前生产版本、滚动 WMAPE、有效周期/真值覆盖、待处置告警/恢复。

#### 10.1.5 算法部署页怎么用

点击“算法开发 → 算法部署”，在“其他场景”选 `load_forecast`。三个页签：

**模型管理**

- 生产模型：当前正式 workflow/version 和 MAPE。
- 影子池：候选 MAPE、连续优于天数；“切换”会真实改变生产身份，必须确认。
- 预上线池：观察进度和生产对比。
- “自动切换”开关：只改配置；“配置”可设观察天数、训练窗口、影子/预上线池上限、冷却期、阈值。
- “版本历史”看 production/shadow/retired；“回滚”有生产模型才可用。

**定时调度**

- 标准顺序：数据拉取→滚动训练→T+1 预测→真值回填→精度检测。
- “启动/停止”改任务登记状态；“触发”异步立即跑一次；“编辑”热更新 cron；“详情”看最近回执/数据证据；“新建任务”需填写名称和 cron。
- 停止任务不会中断已经开始的这一批执行。

**预上线**

- “入池”要填 `candidate_id`、`workflow_id`；观察默认 7 天，容差默认 5%。
- “手动毕业”跳过观察，直接转 shadow；“取消”转 retired。
- 预上线是独立和 production 比，不是候选互相淘汰；毕业后才进影子锦标赛。

**链路缺口**：专用训练页没有把 `model_id` 转成 candidate/workflow 的按钮。要部署，必须先由标准工作流或 AutoResearch 产出有血缘的候选。

5. 点“发起执行”后选择模式，页面会调用项目 API **登记一条 scoped execution** 并跳运行中心；这一步不启动算法。
6. 运行中心显示的是 execution 账本。只有外部真实执行器后续回写节点状态/终态，才会出现真实 pending/running/success/failed 时间线；“用原输入重试”也只新建一条 execution 记录。
7. 真正 labeling 必须从 enhanced workflow/标准画布执行入口运行，并由调用方把节点结果、终态和审核会话写回项目 scope；当前项目页没有 finalize 按钮，也不会自动解析节点结果。

10. “完成审核”只结束审核，不写累计台账；要进入训练集必须点**完成并准入**。
11. 已准入后裁定冻结；精度有有效人工真值才产出，无真值显示“未产出”而不是 0%。

#### 10.2.6 第四步：冻结并训练

1. 进项目“累计训练集”。三层分别是已准入事件、已冻结快照、基于快照的训练结果，不能混为一层。
2. 看“冻结确认区”：纳入/排除、标签/设备/日期分布、快照类型、重复输入。
3. `freezable=true` 才能点“执行冻结”；重复 fingerprint 会幂等命中已有快照。
4. 回“工作流与运行”，新建用途为“训练”的工作流。
5. 绑定不可变数据版本和刚才的冻结快照。同一快照可公平比较多个训练工作流；不绑快照只能实验，不能产正式候选。
6. 项目页“发起执行”仍只登记 training execution。要真实训练，需从 enhanced workflow/标准训练入口启动算法图，并由外部执行方把节点状态、成功终态、`node_results` 和相对 `model_artifact_ref` 回写到项目 execution。

#### 10.2.7 第五步：模型、喂数、回放和精度

项目“模型与治理”四层：

1. 当前检测模型：rolling / Champion / Challenger；另有 inherited baseline（共享原工件、仅对照、不可复验/Promote）。
2. 待复验候选：有完整 provenance 的 training 产物。
3. 实验结果：experiment/validation/sandbox，不能进入正式治理。
4. 治理历史：append-only Promote 审计。

真正运行：

- 生产路径：算法部署→进入路径→“定时调度”→点对应任务“触发”，或等 cron。
- 项目隔离演示：项目“检测与回放”。day/point Sandbox 不写生产、不写累计、不产可治理证据。

然后回项目“审核与精度”处理新会话；平台精度运营看全局/生产只读结果。

#### 10.2.8 第六步：正式复验与 Promote 的当前边界

项目“模型与治理”页目前只能对 provenance 完整的 project candidate 点“发起正式复验”，结果只是 `status=pending`；没有 complete/Promote 前端方法。后端 `complete_verification(passed=...)` 的 passed 由调用方提交，本环境没有自动多窗 compare，因此 caller-marked passed 不能冒充有窗口指标的科学复验。

三条 product slot 的“算法部署”页当前只挂载：

1. **当前生产模型** — `SlotDeployedModelPanel` 只读模型/registry/candidate 信息；
2. **定时调度** — 启停/触发对应 product task。

`SlotClosedLoopActionsPanel` 虽然实现了“构建快照→真实重训→登记 slot candidate→verify-async→evaluation complete→slot Promote”代码，但全仓没有 import/渲染调用方，当前浏览器看不到这些按钮。不要按旧文档寻找“闭环四动作”。

如需治理，必须走经授权的 API/运维流程并区分作用域：

- **Project verification/Promote**：只更新 `(project_id, slot)` 的 project registry；Project Promote 没有 `force=true` 旁路。
- **领域桥**：project candidate finalize 后尝试登记 slot candidate；只有 project verification 被完成为 passed 后，桥才把 slot candidate 设为 slot Challenger，不写 Champion/rolling。
- **Slot verification/Promote**：独立的 slot governance 流程；只有这一层 `set_as_production=true` 才可能改变全局生产 Champion。当前没有可达前端入口。

因此，接手人应先把 slot 治理组件正式挂到部署页、补 `pv_tsc` 生产门控与 UI/E2E 验收，再把它写成可点击操作手册。

#### 10.2.9 三条路径差异

| 维度 | pv_day | pv_point | pv_tsc |
|---|---|---|---|
| 单元 | 设备-天 | 事件点/时间点 | 设备日 288×3 网格 |
| 数据到达 | 等整日 | 逐点到达 | 等完整设备日并重建网格 |

#### 10.2.10 页面状态怎么理解

- Skeleton/Spin：正在请求，先等，不要重复点。
- “暂无”：接口成功但没有记录。
- 红色 Alert：“读取失败”，不是空数据，点重试并看后端。
- 按钮禁用通常表示前置门未满足，例如无快照、provenance 缺失、已有 pending verification 或追平游标；但项目“发起执行”目前**不会**因 `experiment_only` 禁用，真正硬阻断只有 `overall=blocked`。
- `experiment/validation/sandbox` 按目标合同不应治理；当前是否可治理最终看 persisted execution 的 `governance_eligible`，并注意 `experiment_only` 漏洞。
- `validation`/“跨数据集复验”：证明迁移/交互/隔离，治理效力 none，不是模型正式 verification。

硬门：analyzer 必须 `kiro_llm`；undetermined=false；confidence≥0.6；策略必须是 `extra_gap` 或 `pred_fill_dm1`。不满足会走 `_fallback_rca`；confidence 写非数字会直接异常。
