# 光伏故障诊断 —— 代码架构讲解

> 写于 2026-09-14。所有事实来自对运行中后端（`http://localhost:8081`）与工作区代码的实测，
> 关键处附 `file:line` 或接口返回，便于复核。**这不是设计文档**——它描述的是「现在实际长什么样」，
> 包括那些看起来乱的地方。

---

## 0. 一句话

光伏故障诊断有**两条并行主线**：一条是**按 slot（诊断路径）分**的老链路，
一条是**按 project（项目）分**的新工作台；三条诊断路径（pv_day / pv_point / pv_tsc）
同时存在于两条主线上，这是「感觉乱」的头号原因。

---

## 1. 四层主干

项目自己定义的四层（`frontend-sevice/src/config/slotProductConfig.ts` 注释，对齐 design §32）：

```
行业场景 scenario_id  ›  算法方案 solution_id  ›  诊断路径 slot  ›  交付实例 project_id
   renewable-energy        pv_fault              pv_day            proj-16cea45702e2
                                                 pv_point
                                                 pv_tsc
```

- **slot 是「诊断路径」，不是「行业场景」**（`slotProductConfig.ts` 里 `SCENE_WORD = '诊断路径'`，
  历史上被误显示为「场景」，已统一）。
- `pv_fault` 是一个**legacy 聚合槽位**（页面标签写「光伏故障诊断 · legacy」），
  它把三条路径包在一起；**三路径才是产品槽位**（`PV_PRODUCT_SLOTS`）。
- 另有 benchmark 槽位（`benchmark_nasa_smap_msl` 等）复用 pv_point 的工作流拓扑，`governanceEligible: false`。

---

## 2. 两条主线

### 主线 A：`slot` 级链路（老、面向前端「模型部署 / 精度运营」）

```
api/iterative_labeling.py ─┐
api/slot_governance.py     ├─▶ services/iterative_labeling/  (23 py)
api/slot_datasets.py       │   services/slot_governance/     (model_candidates / registry / promote)
api/accuracy_operations.py ┘   services/slot_datasets/       (快照 / 打标 / 台账)
                                └─▶ data/slot_governance/{slot}/registry.json   ← 模型登记
                                    data/slot_datasets/{slot}/...               ← 快照 / 打标
                                    data/iterative_labeling/...                 ← 审核结果
```

- 存储**以 slot 为第一维**：每个 slot 一套 registry / 快照 / 台账。
- 三路径在这条线上是**三个一等公民**：`data/slot_governance/{pv_day|pv_point|pv_tsc}/registry.json`
  各有各的文件。
- 「模型部署」页在 `?slot=pv_tsc` 下读的就是 `GET /api/slot-governance/registry/pv_tsc`
  （实测 network 抓包确认）。

### 主线 B：`project` 级链路（新、面向前端「项目工作台」）

```
api/pv_projects/ (13 py) ─▶ services/pv_projects/ (20 py)
                              └─▶ data/pv_projects/projects/{project_id}/{slot}/...
                                        executions.json / candidates 在 data/slot_governance/? 否 —— 见下
```

- 存储**以 (project_id, slot) 为键**：`data/pv_projects/projects/<pid>/<slot>/`。
- 一条完整故事线：项目 → 挂数据集 → 建工作流 → 预检 → 执行 → 候选 → 复验 → 晋升。
- 它是**领域无关的项目壳**：门禁、scope、仓储、血缘是通用的；
  领域特有语义通过 adapter（`pv-fault/adapters/`、`services/pv_projects/{day,tsc}_adapter.py`）注入。

### 两条线的关系（关键）

```
        ┌─────────────────────────────────────────────┐
        │  三条诊断路径 pv_day / pv_point / pv_tsc      │
        └───────────────┬─────────────────────────────┘
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
  【主线 A：slot 级】              【主线 B：project 级】
  slot_governance/registry/{slot}  pv_projects/projects/{pid}/{slot}
  slot_datasets/{slot}             ├─ executions / candidates / snapshots
  「模型部署 / 精度运营」页读它     └─ 「项目工作台」页读它（/projects/<pid>/…）
```

**两条线此前没有任何通道**——这正是近期加「领域桥」要解决的事（见 §8）。

## 3. 一条数据的端到端旅程（主线 B 为例）

```
用户挂数据集
  └─ POST /api/pv-projects/{pid}/datasets/mount        (services/pv_projects/catalog.py::mount_into_project)
       └─ 数据资产 + 画像 + 不可变数据版本 → data/pv_projects/… 与 data/slot_datasets/…

建训练工作流（复用 canonical 模板）
  └─ POST /api/pv-projects/{pid}/project-workflows      (services/pv_projects/workflows.py)
       └─ 从 data/workflows_enhanced/<template>.json 装载 nodes/edges

预检 → 执行 → 终态
  └─ POST /preflight → POST /executions → POST /executions/{id}/finalize
       └─ 三门禁：工作流存在 / run_mode 与用途合同一致 / preflight 非 blocked

登记候选（要求：执行 success + 工作流绑了**匹配类型**的冻结快照）
  └─ POST /api/pv-projects/{pid}/slots/{slot}/candidates
       └─ 血缘由服务端从 execution 派生；provenance 不全 → 409

复验 → 晋升
  └─ POST …/candidates/{cid}/verifications   (落 pending，不臆造通过)
  └─ POST …/candidates/{cid}/promote         (未授权 production 写入 → 403)
```

## 4. 后端分层约定

| 层 | 位置 | 职责 |
|---|---|---|
| 路由 | `api/*.py`、`api/pv_projects/*.py` | 只做参数校验、scope 构造、错误 → HTTP 映射 |
| 服务 | `services/**` | 业务规则、门禁、血缘派生 |
| 仓储 | `services/pv_projects/repositories.py`、`services/**/store.py` | 落盘、锁、原子写 |
| 数据 | `data/**` | JSON 为主；模型工件是目录 |

惯例（全仓一致）：
- 文件头 `# @AI_GENERATED` 标记 AI 生成段；
- 相对引用持久化，**绝不写机器绝对路径**（`services/pv_projects/paths.py::assert_relative_ref`）；
- 失败一律 fail-closed，错误带 `reason_code`（`api/pv_projects/common.py::unified_error`）。

## 5. 数据存储地图（谁写、谁读）

| 路径 | 归属 | 说明 |
|---|---|---|
| `data/slot_governance/{slot}/registry.json` | 主线 A | 模型登记：champion / challenger / rolling_detect_model / production_path |
| `data/slot_datasets/{slot}/` | 主线 A | 冻结快照、打标提案、台账 |
| `data/iterative_labeling/` | 主线 A | 审核会话与结果、标注注册表 |
| `data/pv_dual_path/model_registry/<slot>.json` | **legacy 聚合** | 只含 `pv_fault` 一个 slot，内部按 `path_models.{legacy_day\|seq_annotation\|tsc}` 分三路 |
| `data/pv_projects/` | 主线 B | `projects/<pid>/<slot>/`；平台级还有 `dataset_catalog.json` |
| `data/deployment/slots.json` | 部署 | 生产/影子/预上线槽位（实测只含 default / load_forecast / load_forecast_e2e_demo，pv_fault 由运行时补） |
| `data/models/{tsc,timeseries_point,seq_annotation,realtime_point_poc}/` | 工件 | 训练产出的模型目录（非单文件） |
| `data/workflows_enhanced/workflow-pv-<path>-{train-eval,label,predict}-v1.json` | 模板 | canonical 工作流图，三路径各一套 |

## 6. 前端页面 → 数据源映射

| 页面 | 路由 | 主数据源 |
|---|---|---|
| 项目工作台 | `/projects/<pid>/…` | 主线 B：`api/pv_projects/*` |
| 算法部署（模型部署） | `/algorithm-deployment?slot=` | 主线 A：`slot-governance/registry/{slot}`、`slot-datasets/*`、`latest-execution` |
| 精度运营 | `/accuracy-operations?slot=` | 主线 A：`slot-overview` / `slot-datasets/observability/*` |
| 迭代标注 | `/iterative-labeling` | 主线 A：`api/iterative_labeling.py` |

两个「治理」页面在 `pv_fault`（legacy）与 `pv_tsc` 等（产品）slot 下的行为**不同**：
`pv_fault` 有「双路径治理」Tab 且只读；产品 slot 只有「当前生产模型 / 定时调度」两个 Tab
（`pages/AlgorithmDeploymentPage.tsx:105-113` 的 `PV_FAULT_TABS` vs `PV_PRODUCT_TABS`）。

## 7. 为什么觉得乱 —— 四个结构性原因

1. **两套体系并行**（§2）。同一个「pv_tsc 模型」在两套存储里都可能有痕迹，
   而两边不互相读：`slot_governance/registry/pv_tsc` ↔ `pv_dual_path/model_registry/pv_fault.json` 的 `tsc` 分支。
2. **三套路径命名**：`pv_tsc`（产品/slot）、`tsc`（legacy modeling_path）、
   `tsc_minirocket`/`MultiRocket`（算法名）。翻译散落多处。
3. **legacy 聚合槽 `pv_fault` 与产品槽并存**，页面按 slot 切换行为，读的端点不同。
4. **AutoResearch 体系**（`services/autoresearch_*.py`，30+ 文件）与光伏诊断**只间接相关**
   （它服务的是通用算法调优），混在同一 `services/` 下，读代码时噪音很大。

## 8. 死代码 / 冗余候选（**仅清单，未删任何东西**）

> 原则：删除是破坏性操作。以下每条都给了可复核证据，请逐条拍板。
> 我**没有**动它们。

### 8.1 确认未挂载的路由（强烈建议清理）

| 项 | 证据 |
|---|---|
| `api/precision_ops.py` | `main.py:57` 原话：「旧 precision_ops 路由**保留源码兼容，但不挂载**；发布状态统一由 deployment_router 管理。」 —— 该文件从未 include 进 app，HTTP 不可达。 |

⚠️ 注意：`services/precision_ops/`（内部服务）**仍被 main.py:252-268 使用**，
**不能**跟着路由一起删。要删的是**路由文件**，不是服务包。

### 8.2 legacy 聚合存储 `pv_dual_path/model_registry`（**不能删**，但要知道它的定位）

我先前**误用**它当三路径的接入点（已改）。但核实后确认它**本身仍在使用**：

- 写入方：`services/iterative_labeling/pv_model_registry.py`（`register_challenger` 等）
- 读取方：`GET /api/iterative-labeling/cumulative-training/modeling-paths?slot=pv_fault`
  （实测返回 `path_models.{legacy_day,seq_annotation,tsc}`，是累计训练那条链的数据源）

**结论：保留**。它的 `path_models` 三分支与产品 slot 是**同一批路径的另一种投影**。
真正的问题是「它与 `slot_governance/registry/{slot}` 之间没有对账」（§8.3）。

### 8.3 已知的结构性冗余（需你决策，不是我单方面能删）

| 冗余 | 证据 | 风险 |
|---|---|---|
| 同一候选存在两套池 | `pv_projects` 的候选在 `data/pv_projects/.../candidates`；`slot_governance` 的候选在 `model_candidates.json`。`register_model_candidate` 要求 `validate_execution_provenance`，**校验不到 pv_projects 的执行**，所以桥只能写 `artifact_ref` 不能写 `candidate_id`。 | 中：不合并的话「模型部署」页的候选列表永远看不到项目侧的候选 |
| `registry.challenger` vs 页面候选列表 | 页面「已登记模型（N）— 生产 / 候选」读的是 `GET /api/slot-governance/model-candidates?slot=`，**不是** `registry.challenger`（实测：桥写入后 registry 有值、页面该区无变化） | 中：桥写 registry 是"对的数据、错的展示位" |

## 9. 建议的收敛方向（供讨论，未实施）

1. **合并候选池**：让 `pv_projects` 的候选登记时也写 `slot_governance` 的候选池
   （或让后者的 provenance 校验接受项目侧执行）。这是 UI 那半截打通的**唯一**正路。
2. **明确两套 registry 的分工**并加对账：产品 slot 用 `slot_governance/registry/{slot}`；
   `pv_dual_path/model_registry` 降级为「累计训练链的内部投影」，不再对外宣称是模型真源。
3. **清理未挂载路由**（§8.1），并把 `services/` 下 AutoResearch 相关文件收进子包
   （如 `services/autoresearch/`），降低读代码噪音。
4. **路径命名的单一真源**：把 `pv_tsc ↔ tsc ↔ modeling_path` 的映射收到一处
   （目前散在 `slotProductConfig.ts`、`pv_candidate_bridge.py`、`cumulative_training.py`）。

## 附：我这次接错的地方（自查）

`9e463a2` 里我把三路径候选全写进了 `data/pv_dual_path/model_registry/pv_fault.json` 的 `path_models`，
以为"用 modeling_path 区分就等于接对槽位了"。实际上产品页面按 **slot** 读
`data/slot_governance/{slot}/registry.json`，所以数据落了但看不见。
`65b722b` 已改为写对应 slot。**教训**：看到「一个存储里有三条路径的分支」不等于
「这就是三路径该写的地方」——要先确认**消费端按什么维度读**。
