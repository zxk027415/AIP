## 0. 先建立全局框架

整条链路只有六步，任何时序故障诊断项目都是这六步：

```
原始测量        → 一条条时序（谁的、什么量、多久一个点）
   ↓
样本构造        → 把长时序切成一个个"样本"（滑动窗口）
   ↓
标签对齐        → 每个样本配一个标签（这是最容易出错的一步）
   ↓
特征表示        → 要么人工算统计量，要么让模型自己学
   ↓
模型训练        → 学"什么形态 = 什么故障"
   ↓
评估 / 预测     → 用正确的划分方式和指标验证，再上线
```

**关键认知**：这六步里，模型（第五步）通常是最不重要的一环。
本项目 9 个模型全跑完，最好和最差差 0.19；而**光是把数据和评估口径修对，
数字就从 0.9579 掉到 0.6162（差 0.34）**。前四步和第六步才是决定成败的地方。

## 1. 任务定义

先分清四件常被混为一谈的事：

| 任务 | 中文 | 输出 | 例子 |
|---|---|---|---|
| Detection | 故障**检测** | 二分类：正常 / 异常 | 这台设备今天有没有问题 |
| **Diagnosis** | 故障**诊断** | 多分类：哪一类故障 | **本项目：12 类故障中的哪一类** |
| Localization | 故障**定位** | 时间/空间位置 | 故障从几点开始、哪个组件 |
| Prognosis | 故障**预测** | 未来会不会坏 | 还有多久失效（剩余寿命） |

**本项目是 Diagnosis（多分类诊断）**，12~13 个类别。

这个区分很重要，因为：
- 检测是二分类，正负样本比可能 1:50，指标看 recall/precision
- 诊断是多分类，要看 macro F1（每类平等对待）
- 定位需要**子天标签**（一天内哪几个时段是故障）。本项目的标注系统**已经支持**
  （`point_labels` 逐点表 + `human_range` 框选），但**存量只有 2 条框选操作 / 293 个点**，
  量级还训不出定位模型。这是**积累量问题，不是架构问题**——继续框选打标就能解决（详见 §4.2）
- 预测需要故障发生前的数据 + 故障发生时间，本项目当前标签存量不支持

老板如果问「能不能提前预警」——**诚实答案是当前标签存量做不了**：
99.79% 的标注点来自历史天级批量导入（`day_label`），没有故障起始时刻。
但要说清这不是系统缺陷：框选打标的通路已经建好并验证过，缺的是标注工作量。

## 2. 数据层

### 2.1 一条时序的三要素

```
一条时序 = 【身份】 + 【测量量】 + 【时间轴】
```

| 要素 | 含义 | 本项目 |
|---|---|---|
| 身份 | 这条序列是谁的 | `(site_id, device_id, branch_id)` |
| 测量量 | 测了什么 | `value`（实测电流）、`i_cal`（理论电流） |
| 时间轴 | 采样间隔 | **5 分钟一个点 → 一天 288 点** |

### 2.2 ★ 序列身份：本项目踩过的最大坑

**这是我在这个项目里发现的第一个 bug，也是最典型的入门错误。**

我一开始以为「一台设备 = 一条时序」，按 `device_id` 分组。实际数据：

| 事实 | 数字 |
|---|---|
| `device_id` 唯一值 | 1,642 |
| `(site_id, device_id, branch_id)` 唯一值 | **2,226** |
| 有多条支路的设备 | 250 台（15.2%），最多 16 条支路 |
| `(device_id, time)` 重复行 | **86,124** ← 证据 |
| `(site,device,branch,time)` 重复行 | **0** ← 这才是主键 |

一台设备挂了 16 条支路，就是 16 条**互相独立的物理时序**。
按 `device_id` 分组再按时间排序，会把 16 条序列**交错混成一条**：

```
错误（按 device_id）：
时间   00:00  00:00  00:00  00:05  00:05  00:05 ...
支路   br1    br2    br3    br1    br2    br3
值     12.1   3.4    8.7    12.0   3.5    8.6
        ↑ 切窗后模型看到的是在三条支路间来回跳的锯齿，不是任何真实波形

正确（按 site|device|branch）：
br1:  12.1  12.0  11.8  ...   ← 一条干净的曲线
br2:   3.4   3.5   3.3  ...
br3:   8.7   8.6   8.5  ...
```

**教训**：动手前先验证 `groupby(主键候选).apply(lambda g: g.time.duplicated().sum())`。
如果有重复时间戳，说明主键选错了。

### 2.3 采样间隔与规整性

```
5 分钟采样 → 一天 288 点 → 一小时 12 点
```

真实数据几乎不会完美规整，本项目实测间隔分布：

| 间隔 | 占比 |
|---|---|
| 5 分钟 | 72.5%（764,692 次） |
| 10 分钟 | 19%（202,312 次，缺一个点） |
| 0 分钟 | 8%（86,124 次 ← 就是上面那个主键 bug 造成的假重复） |

**要处理的三件事**：
1. **缺失点**：插值（线性/前值）或标记后丢弃
2. **重复时间戳**：先查主键是否选错，再考虑去重
3. **不等间隔**：重采样到固定网格，或用能处理不规则序列的模型

本项目做法：`min_coverage=0.9`——窗口内非空点少于 90% 就丢掉这个窗口。

### 2.4 退化数据：一个隐蔽的泄漏源

光伏有个特点：**夜间发电为 0**。所以一整夜的窗口是全零常数序列。

本项目实测：
- 4.42% 的窗口是常数序列
- 其中 **302/303 属于同一个类别**
- 不同设备的全零窗口**内容完全相同**（都是 288 个 0）
- 导致 train/test 出现 **46 个字节级完全一样的窗口**（占 test 3.73%）

这是**数据泄漏**：测试集里有和训练集一模一样的样本，模型零成本答对。

解法：加 `min_std` 过滤，标准差低于阈值的窗口直接丢弃。修完 46 → 0。

**教训**：任何"物理上必然相同"的片段（夜间、停机、检修期）都是潜在泄漏源。

## 3. 单维 vs 多维时序

### 3.1 定义

```
单维（Univariate）：每个样本是一条曲线
    X.shape = [n_samples, 时间长度]
    例：只用 value          → [6852, 288]

多维（Multivariate）：每个样本是多条同步曲线
    X.shape = [n_samples, 时间长度, 通道数]
    例：value + i_cal      → [6852, 288, 2]
```

关键在于**多个通道共享同一个时间轴、同一个标签**。

本项目是**二维（2 通道）多维时序**：

| 通道 | 含义 | 物理意义 |
|---|---|---|
| `value` | 实测电流 | 设备实际输出 |
| `i_cal` | 理论电流 | 按辐照度等条件算出的应有输出 |

### 3.2 为什么多维更难

学术界公认 MTSC（多维时序分类）比 UTSC 难，核心难点是
**如何有效整合多维信息**（[MTSC 综述](https://link.springer.com/chapter/10.1007/978-981-97-5666-7_23)，2024）。
难点有三：

1. **通道间可能强相关也可能无关**，模型得自己判断
2. **不同通道量纲不同**（电流 A、温度 ℃、辐照 W/m²），需要归一化
3. **判别信息可能只在某个通道，或只在通道间的关系里**

### 3.3 处理多维的四种策略

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **拼接（Concatenation）** | 把通道首尾接成一条长序列 | 简单，能直接用单维模型 | 丢失通道同步关系 |
| **通道独立 + 集成** | 每通道单独训一个模型再投票 | 可解释哪个通道有用 | 学不到通道间交互 |
| **真多维卷积** | 卷积核同时跨多个通道 | 能学通道交互 | 参数多，需要更多数据 |
| **通道选择/降维** | 先筛掉无用通道 | 降噪、提速 | 可能丢信息 |

ROCKET 家族用的是**第三种的随机版**：每个卷积核随机选一个通道子集，
不同核看不同通道组合，靠数量覆盖各种可能。

### 3.4 ★ 本项目的通道消融实验

我实测了各种通道组合（严格口径，MiniRocket）：

| 输入 | macro F1（全12类） | Accuracy |
|---|---|---|
| **value + i_cal（2 通道）** | **0.7307** | 0.9732 |
| 仅 value | 0.7072 | 0.9570 |
| 仅 i_cal | 0.5444 | 0.7971 |
| 残差 `value - i_cal`（1 通道） | 0.6687 | 0.9521 |

**怎么读这张表**：
1. `value` 是主信号（单独用 0.7072，接近双通道 0.7307）
2. `i_cal` 单独很弱（0.5444）——理论值本身不含故障信息，合理
3. 加上 `i_cal` 有 +0.024 提升——模型能利用"实测 vs 理论"的偏差
4. **但手工算残差（0.6687）比给两个通道让模型自己学（0.7307）更差**

第 4 点很有教育意义：`value - i_cal` 是物理上最合理的特征（偏差量），
但**手工做减法丢掉了信息**——模型从两个原始通道里能学到的比残差更多
（比如"低辐照时偏差小、高辐照时偏差大"这种条件关系，残差抹掉了）。

**这就是"端到端"相对"手工特征"的优势的一个具体例子。**

### 3.5 可以考虑扩充的通道

本项目目前只有 2 通道，如果能拿到更多测点，值得试：

| 候选通道 | 为什么可能有用 |
|---|---|
| 辐照度 | 直接的驱动量，能区分"没发电"是故障还是没太阳 |
| 组件温度 | 高温降效是一类故障 |
| 电压 | 电流+电压才能算功率，某些故障只在电压上体现 |
| 同串其他支路的均值 | **横向对比**：一串里只有它低 → 该支路故障；全串都低 → 环境因素 |

最后一条特别值得做——这叫**空间参考（spatial reference）**，
是光伏故障诊断的常用技巧，能显著降低误报。

## 4. 标签层

### 4.1 标签粒度的四个层级

**这是整个领域最容易出错、也最影响结果的地方。**

```
① 点级（point-level）      每个时间点一个标签
   time      value  label
   00:00     12.1   normal
   00:05     12.0   normal
   00:10      3.2   fault_A     ← 精确到点
   → 能做：定位、分割、异常检测

② 段级（segment-level）    一个时间区间一个标签
   [10:30 ~ 14:20] → fault_A
   → 能做：段分类，需要先定段边界

③ 窗口级（window-level）   切好的固定窗口一个标签
   window[288点] → fault_A
   → 标准 TSC 形态。本项目模型消费的就是这个

④ 序列级（series-level）   整条时序一个标签
   整台设备一年数据 → "有过 fault_A"
   → 最弱的监督，需要 MIL 等弱监督方法
```

### 4.2 ★ 本项目标签：能力是点级，存量 99.96% 是天级

这里要**分清三个层面**，混起来讲会得出错误结论（我第一版就搞错过）：

| 层面 | 实际情况 |
|---|---|
| **存储架构** | **点级**。`point_labels` 表每个采样点一行，`human_range` 支持任意子天区间 |
| **已做的操作** | **点级确实做过**。库里有 2 条 `human_range` 框选操作，覆盖 293 个点 |
| **训练集信息量** | **99.96% 是天级**。被 4457 条历史 `day_label` 批量导入压倒 |

实测（直接查 `point_labels` / `label_ops` 原表，非快照）：

```
label_ops（active 4479 条）              point_labels（1,058,438 点）
  day_label   整天1440min   4457  99.51%   day_label     1,056,230  99.79%
  human_day   整天1440min     20   0.45%   human_day          1,915   0.18%
  human_range 子天<1440min     2   0.04%   human_range          293   0.028%

设备-天单元 4474 个，其中单元内 label 有变化的 = 2 个（0.04%）
→ (site_id, device_id, branch_id, date) 内 label 唯一比例 = 99.96%
```

**准确说法**：标注人绝大多数是按"设备-天"给标签、广播到当天所有点；
但系统不限于此，人工框选（`human_range`，priority=100）会精确覆盖框内时段，
配合 K4 伴生操作（`human_day`, priority=80, label_id=0）把当日其余时段判为正常。

**为什么"当前做不了定位"**：不是系统只支持天级，而是**子天标签存量太少**
（2 条操作 / 293 点）。要做定位，继续框选打标即可，无需改任何代码。

下面四个后果是**基于当前存量**（99.96% 天级）的实测结论。
如果后续子天标签大量积累，这几条都需要重新评估：

#### 后果 1：窗口长度必须匹配标签粒度

当前存量 99.96% 是天级 → 一天（288 点）的窗口恰好对应一个标注单元。
我实测缩短窗口：

| window / stride | 窗口数 | macro F1 | 变化 |
|---|---|---|---|
| **288 / 72（1天）** | 2,918 | **0.6495** | 基线 |
| 144 / 36（半天） | 6,902 | 0.5164 | **−0.133** |
| 72 / 18（6小时） | 12,469 | 0.4892 | **−0.160** |

**窗口数翻 4.7 倍，精度掉 0.13。**

原因：半天窗口只看到一天的一部分，但被要求预测**整天**的标签。
如果故障发生在下午，上午那个窗口就是"正常波形 + 故障标签"= 标签噪声。

**这是"标签粒度决定窗口长度"的直接证据。**

#### 后果 2：有效样本量远小于窗口数

```
独立标注单元（device-branch-day）：4,457 个
切出的窗口数（stride=72，75% 重叠）：6,852 个
虚增倍数：1.54x
```

同一天切出的 3~4 个窗口**共享同一个标签、内容 75% 重叠**，
它们不是独立样本。做统计推断时有效样本数是 4,457，不是 6,852。

**后果**：置信区间比窗口数暗示的更宽。这也是我们方差高达 std=0.075 的原因之一。

#### 后果 3：无法做故障定位

天级标签只能告诉你"这一天有 fault_A"，不知道从几点开始。
所以本项目**做不了定位和预警**，只能做"日级诊断"。

要做定位必须重新标注到点级或段级。

#### 后果 4：多标签窗口需要聚合策略

如果窗口跨了两天（标签不同），得决定用哪个标签：

| 策略 | 逻辑 | 适用 |
|---|---|---|
| **众数 + 纯度过滤** | 取占比最高的标签；占比低于阈值就丢弃该窗口 | 默认，本项目用这个（`purity_threshold=0.7`） |
| 故障优先 | 只要有 ≥N 个故障点就标为故障 | 宁可误报不可漏报的场景 |
| 边界对齐 | 让窗口起点对齐标签变化时刻 | 减少混合窗口 |

本项目实测 86.6% 的窗口纯度 = 1.0（完全单一标签），说明窗口基本是日对齐的。

### 4.3 弱监督：当标签比你想要的粗

「只有粗粒度标签，却想要细粒度输出」是一个专门的研究方向，叫
**弱监督 / 多示例学习（MIL, Multiple Instance Learning）**。

思路：把一个窗口看成一个"包（bag）"，里面的时间点是"示例（instance）"。
已知包的标签，推断哪些示例导致了这个标签。
[TreeMIL](https://arxiv.org/html/2401.11235) 等方法在只有序列级标签的情况下
预测点级异常，相比之前的 SOTA 平均提升 32.3% F1。

**对本项目的意义**：如果将来要做定位而又不想重新标注，MIL 是一条路。
但当前阶段（只做日级诊断）不需要。

### 4.4 类别不平衡

本项目 test 集类别分布（1,254 个窗口）：

| label | 窗口数 | 占比 |
|---|---|---|
| 1 | 602 | 48.0% |
| 11 | 230 | 18.3% |
| 0 | 181 | 14.4% |
| 2 | 95 | 7.6% |
| 8 | 36 | 2.9% |
| 4 | 25 | 2.0% |
| 7 | 24 | 1.9% |
| 6 | 21 | 1.7% |
| 3 | 15 | 1.2% |
| 12 | 3 | 0.2% |
| 9 | **1** | 0.08% |
| 10 | 9 | 0.7% |

**前两类占 66%，最少的类只有 1 个窗口。**

这直接导致：
1. **accuracy 严重虚高**——多数类基线（永远猜 label 1）accuracy 就有 **0.4665**
2. **macro F1 方差大**——只有 1 个样本的类，对了 F1=1、错了 F1=0，没有中间态
3. 需要 `class_weight` 加权或过采样

## 5. 样本构造

### 5.1 滑动窗口

```
原始序列: ──────────────────────────────────────→ 时间
          |←── window_length ──→|
样本1:    [■■■■■■■■■■■■■■■■■■■■]
                |←stride→|
样本2:          [■■■■■■■■■■■■■■■■■■■■]
样本3:                [■■■■■■■■■■■■■■■■■■■■]
```

两个参数：

| 参数 | 含义 | 本项目 |
|---|---|---|
| `window_length` | 窗口点数 | **288**（= 1 天，匹配标签粒度） |
| `stride` | 每次滑动多少点 | **72**（= 6 小时，75% 重叠） |

窗口数公式：`(序列长度 − window_length) // stride + 1`

### 5.2 stride 怎么选

| stride | 重叠率 | 效果 |
|---|---|---|
| = window_length | 0% | 样本独立，但数量少 |
| = window_length / 2 | 50% | 折中 |
| **= window_length / 4** | **75%** | **本项目：样本多，但相关性高** |
| 很小 | >90% | 样本极多但高度冗余，等于变相过采样 |

**重要认知**：减小 stride 增加的是**相关样本**，不是独立信息。
本项目 stride 从 72 降到 36，窗口从 2,918 涨到 5,613，
但严格口径下 F1 从 0.6495 **降到** 0.5730。

原因：重叠窗口让模型看到近乎重复的样本，加剧过拟合；
而且如果重叠窗口跨了 train/test 边界，就是直接泄漏。

### 5.3 过滤规则

本项目的窗口三道过滤：

```python
1. 覆盖率： 窗口内非 NaN 比例 >= min_coverage (0.9)
2. 退化：   首通道标准差 >= min_std (1e-6)     ← 剔夜间全零
3. 纯度：   标签众数占比 >= purity_threshold (0.7)
```

实测效果：全量 1642 设备切出 **6,852** 窗口（未过滤退化）→ **6,533**（加 min_std）。
理论上限 7,353。

## 6. 特征层

### 6.1 核心问题：聚合 vs 原始

这是本项目立项的根本命题。

```
路线 A（聚合特征 / 传统）：
  288 点曲线 → 算统计量 → [均值, 方差, 最大, 最小, 分位数, ...] → 随机森林
                             ↑ 50 个数字
  ❌ 时间顺序丢失

路线 B（原始时序 / 端到端）：
  288 点曲线 → 直接喂给模型 → 模型自己找形态
  ✅ 时间顺序保留
```

**为什么顺序重要**——一个经典例子：

```
形态甲：先平稳后骤降    ▔▔▔▔▔╲___
形态乙：先骤降后恢复    ___╱▔▔▔▔▔

两者的均值、方差、最大、最小、分位数【几乎完全一样】
但物理含义完全不同（甲=故障发生，乙=故障恢复）
```

聚合特征分不出这两个，端到端模型能分。

### 6.2 ★ 本项目的时间打乱消融实验

怎么证明模型真的在用时间顺序？**把窗口内 288 个点随机重排，看精度掉多少。**

| | macro F1 | Accuracy |
|---|---|---|
| 正常顺序 | 0.7283 | 0.9490 |
| **随机打乱** | **0.4122** | 0.7863 |

**F1 掉 0.32。** 这证明：
1. 模型确实在用时序形态，不是只看幅值分布
2. 本项目"时序建模"这个立项前提是站得住的

**这个实验只需 5 行代码，是任何时序项目都该做的 sanity check。**
如果打乱后精度不掉，说明你根本不需要时序模型，用聚合特征就够了。

### 6.3 学术界的八大流派

[Bake off redux](https://link.springer.com/article/10.1007/s10618-024-01022-1)（2024）
按"提取什么特征"把 TSC 算法分成八类（原 5 类 + 新增 3 类）：

| 流派 | 原理 | 代表算法 | 本项目 |
|---|---|---|---|
| **Distance** 距离 | 直接比较两条曲线的相似度（DTW 弹性距离） | 1-NN + DTW | 未测（慢） |
| **Interval** 区间 | 从随机时间区间提取统计量 | TSF, CIF, DrCIF, QUANT | 未测 |
| **Shapelet** 形状子 | 找最有判别力的子序列片段 | STC, RDST | 未测 |
| **Dictionary** 字典 | 把子序列离散成"词"，统计词频（词袋法） | BOSS, WEASEL, TDE | 未测 |
| **Convolution** 卷积 | 大量卷积核提特征 + 线性分类器 | **ROCKET / MiniRocket / MultiRocket** | **✅ 最终选型** |
| **Feature** 特征 | 自动算大批统计特征 + 分类器 | TSFresh, Catch22, FreshPRINCE | 部分（聚合基线） |
| **Deep Learning** 深度 | 神经网络端到端 | InceptionTime, ResNet, CNN-LSTM | ✅ 全部落败 |
| **Hybrid** 混合 | 集成多个流派 | HIVE-COTE 2.0 | 未测（太慢） |

**benchmark 共识**：HIVE-COTE 2.0 精度最高但极慢；
MultiRocket 精度接近 HC2 而快几个数量级；InceptionTime 是深度学习里最强的。

### 6.4 本项目的聚合特征基线

我做了个对照：13 个手工统计量 + 决策树

```python
特征 = [value的均值/标准差/最大/最小,
        i_cal的均值/标准差/最大/最小,
        比值(value/i_cal)的均值/标准差,
        残差(value-i_cal)的均值/标准差,
        零值占比]
```

| | macro F1 | balanced Acc |
|---|---|---|
| 聚合特征 + 决策树 | 0.5222 ± 0.0520 | 0.6335 ± 0.0879 |
| **MultiRocket** | **0.6315 ± 0.0750** | 0.7747 ± 0.1181 |
| **配对差** | **+0.1094 ± 0.0669（9/10 划分胜出）** | |

**这 +0.11 就是"时序建模"相对"聚合特征"的真实价值。**

⚠️ 但有个重要发现：**这个优势只在严格评估口径下才显现**：

| 评估口径 | 聚合特征 | MultiRocket | 差 |
|---|---|---|---|
| 宽松（按设备划分，同期） | 0.7747 | 0.7635 | **−0.01（聚合特征"赢"）** |
| 严格（未见日期 + 未见设备） | 0.4316 | 0.7635 | **+0.33** |

宽松口径下聚合特征甚至略好。原因是聚合统计量在"同期同设备群"上
过拟合了设备/时段特有的幅值水平；换到未见设备 + 未见日期就崩了。

**教训：评估口径错了，会得出完全相反的技术结论。**

## 7. 模型层

### 7.1 ROCKET：本项目最终选型的家族

ROCKET 是 TSC 领域的"强基线"，思路反直觉但极其有效。

#### 核心思想

> 不要费心设计卷积核，随机生成一万个，总有一些能撞上有用的形态。

#### ROCKET 机制

```
输入：一条 288 点曲线
  ↓
生成 10,000 个【随机】卷积核，每个核随机化：
    - 长度：从 {7, 9, 11} 里随机选
    - 权重：从正态分布 N(0,1) 采样
    - 偏置：从均匀分布 U(-1,1) 采样
    - 膨胀率(dilation)：随机 → 让核能看不同时间尺度
    - padding：随机
  ↓
每个核在曲线上滑动卷积，得到一条响应序列
  ↓
从每条响应序列提取 2 个数：
    - max：最大响应（这个形态最强出现在哪）
    - PPV（Proportion of Positive Values）：响应为正的比例
             ↑ 这个才是关键！表示"这个形态在序列中占多大比例"
  ↓
10,000 核 × 2 个数 = 20,000 维特征向量
  ↓
Ridge 线性分类器（带交叉验证选正则强度）
  ↓
输出类别
```

**为什么有效**：
1. **膨胀率随机化**让不同核覆盖不同时间尺度（几分钟的骤降 vs 几小时的衰退）
2. **PPV 是精髓**——它测的是"形态占比"，比只看最大值鲁棒得多
3. **不需要反向传播**，只有最后的线性分类器要训练 → 极快
4. 高维随机特征 + 线性分类器，**小样本下不易过拟合**（这是它打败深度模型的关键）

#### MiniRocket：更快且几乎确定性

```
改进：不再随机生成核，而是用【固定的 84 个核】
      - 长度固定 9
      - 权重只取两个值 {-1, 2}
      - 84 = 从 9 个位置里选 3 个设为 2 的组合数 C(9,3) = 84
只用 PPV 一个池化算子
```
论文结论：MiniRocket 比同等精度的方法都快得多，
建议**作为 ROCKET 的默认版本**使用。

#### MultiRocket：本项目最终选型

```
MiniRocket 基础上加两个扩展：
① 多池化算子（不只 PPV）：
     - PPV  正值比例
     - MPV  正值均值
     - MIPV 正值位置的平均索引  ← 带位置信息！
     - LSPV 最长连续正值段长度  ← 带持续性信息！
② 同时对【一阶差分序列】也做一遍
     → 原序列看"水平"，差分序列看"变化率"
约 50,000 维特征
```

MIPV 和 LSPV 是 MultiRocket 强于 MiniRocket 的关键——
它们编码了**"这个形态出现在什么位置"和"持续了多久"**，
这正是故障诊断需要的信息。

本项目实测 MultiRocket 优于 MiniRocket：配对差 **+0.0782 ± 0.0665，9/10 划分胜出**。

### 7.2 深度模型

#### CNN 系（ResNet-1D / InceptionTime）

```
输入 [batch, 通道, 时间]
  ↓
1D 卷积层堆叠（卷积核在时间轴上滑动，学局部形态）
  ↓
全局池化（把时间维压掉）
  ↓
全连接 + Softmax
```

**InceptionTime** 的特色：每层并行放多个不同长度的卷积核
（kernel=10/20/40），同时看多个时间尺度，最后集成 5 个模型。

#### CNN-LSTM 系

```
1D-CNN 提局部形态（"5 个点内的骤降"）
  ↓
LSTM 抓长程时间依赖（"骤降之后有没有恢复"）
  ↓
全连接分类
```

光伏文献里这个架构很常见（[CNN-LSTM 光伏 DC 故障诊断](https://www.mdpi.com/2079-9292/14/6/1205/xml)，2025）。

#### ★ 但在本项目全部落败

GPU 服务器 + `epochs=200`（训练轮数和算力都给足）的结果：

| 模型 | macro F1 | vs MultiRocket | 胜出划分 |
|---|---|---|---|
| **MultiRocket** | **0.6162 ± 0.0710** | baseline | — |
| Inception 单模型 | 0.5097 ± 0.0845 | −0.1065 | 2/10 |
| InceptionTime 集成 | 0.4967 ± 0.0564 | −0.1195 | **0/10** |
| CNN-BiLSTM-Attention | 0.4546 ± 0.0592 | −0.1616 | 1/10 |
| ResNet-1D | 0.4256 ± 0.0470 | −0.1906 | **0/10** |
| CNN-LSTM | 0.4242 ± 0.0470 | −0.1920 | **0/10** |

**三个模型 0/10，一次都没赢过。**

#### 为什么深度模型输了

**根本原因是样本量。** 严格口径下训练集只有约 **870 个窗口**。

| 方法 | 需要训练的参数 | 小样本表现 |
|---|---|---|
| ROCKET 家族 | 只有最后的线性分类器 | **稳** |
| 深度网络 | 几十万到几百万参数 | 欠拟合 / 过拟合 |

深度学习通常需要**数千到数万**样本才能发挥。870 个远不够。

**重要区分**（这是我在项目中修正过的一个因果解释）：
- ❌ 不是"实验设计得不好"
- ✅ 是"可用数据本身就这么多"

**推论**：如果将来窗口量增长到数万级，深度模型值得重新评估。
当前数据规模下可以关闭这条线。这个话要说清楚，否则听起来像是没试明白。

## 8. 训练与预测流程

### 8.1 训练流程

```python
# ① 加载：按【完整序列主键】分组，绝不能只按 device_id
df = load(...)
series_keys = ["site_id", "device_id", "branch_id"]

# ② 切窗
X, y, meta = sampler.transform_multi_device(df)
# X.shape = [6533, 288, 2]   ← [样本数, 时间长度, 通道数]
# y.shape = [6533]
# meta 记录每个窗口来自哪条序列、哪个时间段（划分时要用！）

# ③ 预处理
X = preprocess(X, method="per_sample_zscore")
```

**关于归一化的一个要点**：本项目用 **per-sample z-score**
（每个窗口独立用自己的均值和标准差归一化）。

这样做的好处是**不会泄漏**——如果用全局均值/标准差，
那个统计量是从整个数据集（含测试集）算出来的，属于泄漏。
per-sample 归一化每个样本只用自己的信息，天然安全。

```python
# ④ 划分（关键！见第 9 节）
X_tr, y_tr, X_te, y_te = split_strict(X, y, meta)

# ⑤ 训练
model = MultiRocketClassifier()
model.fit(X_tr, y_tr)

# ⑥ 评估
preds = model.predict(X_te)
f1 = f1_score(y_te, preds, average="macro", labels=全部类别)  # labels 必须给！

# ⑦ 持久化：模型 + 窗口配置一起存
save(model, metadata={
    "window_length": 288, "stride": 72,
    "channels": ["value", "i_cal"],
    "preprocess": "per_sample_zscore",
})
```

### 8.2 ★ 为什么必须把窗口配置和模型一起存

**这是新手最容易忽略、上线后最容易出事的地方。**

模型的输入维度是固定的。用 288 点训练的模型，预测时也必须喂 288 点。

```
类比：
  YOLO 用 640×640 训练 → 预测时也得 resize 到 640×640
  时序模型用 288 点训练 → 预测时也得给 288 点
```

如果模型 A 用 288 训练、模型 B 用 576 训练，部署时不查 metadata 就会搞混，
喂错长度直接报错或输出垃圾。

所以模型产物必须是**自描述**的：
```json
{
  "model": "<权重>",
  "metadata": {
    "window_length": 288,
    "stride": 72,
    "channels": ["value", "i_cal"],
    "preprocess": "per_sample_zscore",
    "min_std": 1e-6
  }
}
```

### 8.3 预测流程

```python
predictor = TSCPredictor("path/to/model")   # 自动读出窗口配置

# 方式一：单窗口预测（取最近 288 点）
result = predictor.predict_device(device_timeseries)
# → {label: 1, confidence: 0.87, window_start: ..., window_end: ...}

# 方式二：多窗口投票（更鲁棒）
result = predictor.predict_device_multi_window(device_timeseries, stride=72)
# → 切出 8 个窗口各预测一次，取众数或平均概率
```

**多窗口投票为什么更鲁棒**：单个窗口可能恰好卡在故障边界导致判错，
多个窗口投票能平掉这种偶然。

### 8.4 训练/预测一致性清单

上线前必须逐条核对：

- [ ] `window_length` 一致
- [ ] `channels` 顺序和数量一致
- [ ] 归一化方式一致
- [ ] 过滤规则一致（`min_coverage` / `min_std`）
- [ ] 序列分组主键一致
- [ ] 标签编码映射一致（label_id ↔ 业务故障名）

**任何一条不一致，预测结果就是无意义的。**

## 9. 划分与泄漏

### 9.1 时序数据不能随机划分

这是**最容易犯、后果最严重**的错误。

```
❌ 随机划分（sklearn 默认的 train_test_split）
   同一天切出的重叠窗口，一部分进 train、一部分进 test
   → 测试集里有和训练集 75% 重叠的样本 → 精度虚高
```

### 9.2 三种正确划分口径（严格程度递增）

| 口径 | 隔离什么 | 模拟什么场景 | 本项目实测（MiniRocket） |
|---|---|---|---|
| **按设备** | 设备不重叠 | "诊断没见过的设备，但还是同一批天" | 0.7623 |
| **按时间** | 日期不重叠 | "诊断没见过的日期，但设备是老的" | 0.7147 |
| **双隔离（strict）** | 设备+日期都不重叠 | **真实生产：诊断没见过的设备 + 没见过的日期** | **0.6940** |

**从宽松到严格，精度递减。宽松口径给出的是"实验室数字"，不是上线能达到的水平。**

#### ★ 别把「时间隔离」误读成「预测未来」

这里有个极易混淆的点（我自己写文档时就说错过一次）：

| 「预测」的两种含义 | 英文 | 含义 | 本项目 |
|---|---|---|---|
| 任务类型 | Prognosis / Forecasting | 判断设备**将来**会不会坏、剩余寿命 | **没做，数据也不支持** |
| 推理动作 | predict / inference | 模型对输入吐出一个类别，即 `model.predict(X)` | **做了，任何分类都有这一步** |

**本项目从头到尾是 Diagnosis（诊断）**：输入一段**已经发生**的时序，输出它属于哪一类故障。
时间方向是**回看**，不是前瞻。

那为什么诊断任务还要按时间隔离？因为**上线后诊断的对象永远是新时间段的数据**：

```
8/03  用 05-06 ~ 05-12 的数据训练完，部署
       ↓
8/04  当天数据进来 → model.predict() → 「这台设备今天是哪类故障」
       ↑ 8/04 这一天的辐照、温度、云层，模型训练时从没见过
```

任务是「诊断今天已经发生的事」，但「今天」对模型永远是陌生的一天。
如果评估时 train 和 test 共享日期，模型能利用「05-08 下午 14:00 一片云过来、
全站曲线同时下凹」这种**当天共享气象条件**去猜标签 —— 而上线后这条捷径不存在。

**所以时间隔离的目的是：让 test 集里的「天」对模型是陌生的，和上线后一致。
不是因为任务变成了预测未来。**

### 9.3 ★ 本项目的完整泄漏排查

老板质疑 96.77% 太高之后，我逐项排查了所有泄漏假设。这份清单可以直接复用：

#### 已排除的

| 假设 | 怎么验的 | 结果 |
|---|---|---|
| **标签规则泄漏**：标签是不是由 `value`/`i_cal` 阈值算出来的？（等于把答案当特征） | 查数据生成流程 | **排除**。源数据无 label，标签由独立表贴回，两者是原始测量值 |
| **日期查表泄漏**：train/test 共享全部日期，模型会不会靠"认日期"作答？ | 只用日期查表预测 | **排除**。Acc=0.6924 / F1=0.3062，远低于模型 |
| 同上，用 (站点, 日期) 查表 | 同上 | **排除**。Acc=0.7094 / F1=0.4229 |

**「查表基线」这个技巧非常好用**：如果只用某个元信息（日期、设备ID、站点）
查表就能达到接近模型的精度，说明模型学的是那个元信息而不是信号。

#### 已确认并修复的

| 问题 | 详情 | 影响 |
|---|---|---|
| **指标口径错误** | `f1_score(average="macro")` 没指定 `labels=`，sklearn 只在 test 出现的类上平均，缺席的稀有类被静默排除 | 同一次预测：0.8841 vs 全类 **0.7367**，虚高 **0.147** |
| **退化窗口泄漏** | 夜间全零窗口在不同设备间内容完全相同 | train/test 46 个字节级重复窗口（占 test 3.73%） |
| **accuracy 被不平衡虚高** | 多数类基线 accuracy 就有 0.4665 | 改用 macro F1 + balanced accuracy |

### 9.4 隔离自检代码

每次划分后都应该自动校验，别靠人肉检查：

```python
def check_isolation(X, meta, tr, te):
    # ① 设备是否隔离
    device_overlap = len(set(meta.iloc[tr].device_id) & set(meta.iloc[te].device_id))
    # ② 日期是否隔离
    date_overlap = len(set(meta.iloc[tr].date) & set(meta.iloc[te].date))
    # ③ 有没有字节级完全相同的窗口（最容易被忽略）
    h_tr = {hash(X[i].tobytes()) for i in tr}
    identical = sum(hash(X[i].tobytes()) in h_tr for i in te)

    assert device_overlap == 0
    assert date_overlap == 0
    assert identical == 0
```

第 ③ 条是我在本项目里发现 46 个重复窗口的方法。**强烈建议每个项目都加上。**

## 10. 评估指标

### 10.1 为什么本项目不能用 accuracy

```
本项目 test 集：label 1 占 48.0%，label 1+11 占 66.3%

"永远猜 label 1" 这个白痴基线：
    accuracy = 0.4665   ← 看着还行！
    macro F1 = 0.0530   ← 原形暴露
```

**在不平衡数据上，accuracy 会奖励"只学多数类"的模型。**

### 10.2 该用什么

| 指标 | 定义 | 什么时候用 |
|---|---|---|
| **macro F1** | 每类算 F1 再简单平均（**每类平等**） | **多分类诊断的主指标** |
| **balanced accuracy** | 每类的 recall 再平均 | 辅助主指标，直观 |
| weighted F1 | 按类别样本数加权平均 | 关心整体命中率时 |
| accuracy | 整体正确率 | 类别平衡时才有意义 |
| per-class F1 | 每类单独的 F1 | 定位哪类学不好 |
| 混淆矩阵 | 谁被误判成谁 | 分析错误模式，找业务上可接受的混淆 |

本项目最终报告用 **macro F1（全类）+ balanced accuracy**，不报 accuracy。

### 10.3 ★ macro 指标必须指定 labels=

**这是本项目虚高 0.147 的直接原因，也是最隐蔽的坑之一。**

```python
# ❌ 错误：sklearn 只在 test∪pred 出现的类上平均
f1_score(y_true, y_pred, average="macro")
# → 0.8841

# ✅ 正确：固定在完整标签空间
f1_score(y_true, y_pred, average="macro", labels=全部12个类, zero_division=0)
# → 0.7367
```

差 **0.147**。原因：稀有类（label 9 只有 1 个窗口）如果没进 test，
默认口径就把它排除在平均之外；而正确口径下这些类 F1=0，会拉低 macro。

**为什么正确口径更诚实**：模型对那些类**确实一个都没学会**，
不该因为测试集里恰好没抽到就免于计分。

### 10.4 ★ 单次划分的数字不可信

本项目最惨痛的教训之一：

```
同一协议、同一数据、只换随机种子，跑两次：
    第一次 macro F1 = 0.7635
    第二次 macro F1 = 0.6495
    差 0.11
```

跑 10 个种子后：**std = 0.075，极差 0.20**。

**所以任何单个数字都不能对外汇报，必须给 mean ± std（至少 10 次划分）。**

### 10.5 ★ 比较两个模型要用"配对差"

**我在这个项目里犯过并纠正的统计错误。**

```
❌ 错误做法：
   模型A = 0.6315 ± 0.0750
   模型B = 0.5534 ± 0.0789
   "差 0.078 大于两者标准差，所以 A 更好"
   → 错！忽略了两个模型在同一划分上的相关性

✅ 正确做法（逐划分配对差）：
   for 每个划分:
       diff = A在这个划分的F1 - B在这个划分的F1
   统计 diff 的均值、标准差、A 胜出的次数

   结果：+0.0782 ± 0.0665，9/10 划分 A 胜出
```

**为什么配对差更可靠**：同一划分上比较，消除了"这个划分本身难不难"的影响。
有些划分对所有模型都难，有些都简单，配对差把这个共同因素抵消了。

## 12. 老板可能问的问题及答法

### Q1：精度多少？

> 严格口径下 macro F1 = 0.6162 ± 0.0710，balanced accuracy = 0.7650。
>
> 这里要说明两件事。第一，用的是"训练未见日期 + 训练未见设备"的严格划分，
> 也就是模拟真实上线场景（上线后诊断的总是新的一天、可能是新装的设备）；
> 如果用常见的随机/按设备划分，数字会高到 0.76，但那个数字上线达不到。
> 第二，不报 accuracy——本项目 accuracy 有 0.89，
> 但多数类基线（永远猜最多的那类）就有 0.4665，accuracy 会严重高估能力。

**如果老板追问「这是在预测未来吗」**：不是。任务是**故障诊断**，输入是一段
**已经发生**的时序，输出它属于哪类故障。"未见日期"说的是**评估协议**——
test 用训练时没出现过的日期，因为上线后模型面对的总是新的一天。
真正的"预测未来"（Prognosis，判断设备将来会不会坏）本项目没做，
当前标签也不支持（99.79% 标注点来自天级批量导入，没有故障起始时刻）。

### Q2：为什么不是 90% 以上？

> 三个原因。
>
> 一是任务本身难：12 个类别，其中 3 个类的样本数是个位数（最少的只有 1 个窗口），
> macro F1 对这些类特别敏感。
>
> 二是评估口径严格：同样的模型在宽松口径下是 0.76，我们主动选了最严的口径汇报。
>
> 三是数据量限制：严格口径下训练集只有约 870 个窗口。
>
> 顺便说，我们一开始报过 0.9579，后来查出是数据 bug 加指标口径错误造成的虚高，
> 已经修正。这个我有完整的排查报告。

### Q3：有没有数据穿越？

> 系统排查过，有报告。
>
> 排除了两类：标签规则泄漏（标签不是由输入特征算出来的）、
> 日期查表泄漏（只用日期查表只能到 0.69，远低于模型）。
>
> 发现并修复了两个真问题：一是夜间全零窗口在不同设备间内容完全相同，
> 造成 46 个测试样本和训练样本字节级重复，已加过滤剔除；
> 二是 macro F1 没指定完整标签空间，导致稀有类被静默排除、虚高 0.147。
>
> 现在每次划分都有自动隔离自检：设备重叠、日期重叠、字节级重复窗口三项必须为 0。

### Q4：为什么用 MultiRocket 这种"老"方法，不用深度学习 / Transformer？

> 试过了，9 个模型全跑完，深度模型全部落败。
>
> 在 GPU 上跑了 ResNet、InceptionTime（含 5 模型集成）、CNN-LSTM、
> CNN-BiLSTM-Attention，训练轮数给到 200。结果是三个模型在 10 次划分里
> 一次都没赢过 MultiRocket，配对差 −0.11 到 −0.19。
>
> 原因是样本量：严格口径下训练集约 870 个窗口，深度网络有几十万参数，
> 这个量级学不动。ROCKET 家族只需要训练最后的线性分类器，小样本下更稳。
>
> 补充一句：如果将来数据量上到数万窗口级别，深度模型值得重新评估。
> 现在不是方法不行，是数据量不到。

### Q5：时序建模比原来的随机森林好多少？值得做吗？

> 相对聚合特征基线（就是随机森林那条路线的特征形态），
> macro F1 提升 +0.1094 ± 0.0669，10 次划分里 9 次胜出。
>
> 有个关键发现：这个优势只在严格口径下才看得出来。宽松口径下聚合特征
> 甚至略微领先（0.7747 vs 0.7635），但换到"未见设备 + 未见日期"，
> 聚合特征崩到 0.4316，时序模型还有 0.7635。
>
> 原因是聚合统计量过拟合了设备和时段特有的幅值水平，换设备就失效；
> 时序模型学的是形态，泛化更好。
>
> 所以结论是值得做，但如果用宽松口径评估会得出相反结论。

### Q6：怎么证明模型真的在用时序信息，不是碰巧？

> 做了时间打乱消融：把每个窗口内 288 个点随机重排，其他都不变。
> macro F1 从 0.7283 掉到 0.4122，accuracy 从 0.9490 掉到 0.7863。
>
> 打乱后大幅退化，说明模型确实依赖时间顺序，不是只看幅值分布。
> 这也验证了立项前提。

### Q7：能上线吗？

> 建议先注册为 fallback_path（备用路径），不直接替换生产。
>
> 还有一个开放项：现在所有数字都来自一个数据块——241 台设备、单站点、7 天。
> 跨站点、跨季节的泛化能力没验证过。
>
> 补齐材料已经准备好了：2021-11 那一批 7 天全连续、5 个站点、304 台设备、
> 731 个待标注单元，标完就能做跨站点验证。这是提升到生产路径前应该做的。

### Q8：为什么数据只有 35 天？能不能多搞点？

> 全数据集 105 万行看着不少，但只有 35 个不同日期，散落在 10 个不连续的簇里，
> 日期密度只有 0.052。所以做不了时间切分验证——按时间切完测试集只剩 10 个窗口。
>
> 我扫过所有数据源。带标签的数据已经 100% 合并进主数据集了，简单拼接没有增量。
> 但 train_ori 下还有 552,664 行未标注数据，覆盖 9 个站点，能扩 52%，
> 需要走标注流程。
>
> 另外，要验证跨季度漂移必须有连续 30 天以上的数据，现有所有数据源
> 最长连续段只有 9 天，这个靠拼接解决不了，得重新采集。

### Q9：训练要多久？要 GPU 吗？

> MultiRocket 不需要 GPU，训练 20 到 150 秒（看样本量）。
> 这也是选它的一个原因——生产环境需要频繁重训，秒级训练很实用。
>
> 深度模型才需要 GPU，而且在 Windows 上 TensorFlow 官方不支持 GPU，
> 4 个深度模型 10 折要 2.5 到 3 小时，所以那部分实验放到 Linux GPU 服务器上跑。

### Q10：这套东西可靠吗？会不会又发现问题？

> 做了三件事保证可靠性。
>
> 一是每个查出的 bug 都留了回归测试，现在 97 个测试用例，
> 直接锚定跨支路混合、笛卡尔积、sample_id 撞车、退化窗口、
> 严格口径隔离性质这些具体问题。
>
> 二是跨环境复现：本机 Windows CPU 和服务器 Linux GPU 两套完全不同的
> 依赖栈，baseline 差 0.0014，说明没有环境相关的隐藏问题。
>
> 三是防误用机制：单次划分的数字有三道拦截——代码注释警告、
> API 返回 warning、前端显示黄色警告条，避免有人拿宽松口径的数字去汇报。

## 附：可以直接复用的自检清单

新做一个时序项目，按这个顺序检查：

**数据层**
- [ ] 序列主键选对了吗？（`groupby(主键).time.duplicated().sum()` 应为 0）
- [ ] 采样间隔的实际分布是什么？（不要假设规整）
- [ ] 有没有"物理上必然相同"的片段？（夜间/停机 → 潜在泄漏）

**标签层**
- [ ] 标签的**真实**粒度是什么？（存储粒度 ≠ 内容粒度）
- [ ] 窗口长度和标签粒度匹配吗？
- [ ] 独立标注单元有多少个？（不是窗口数）
- [ ] 类别分布？最少的类有几个样本？

**特征/模型层**
- [ ] 做时间打乱消融了吗？（不掉 → 不需要时序模型）
- [ ] 有聚合特征基线做对照吗？
- [ ] 有多数类基线吗？（accuracy 的下限）

**划分层**
- [ ] 是按时间/实体划分，不是随机划分？
- [ ] 隔离自检三项：设备重叠 / 日期重叠 / 字节级重复窗口
- [ ] 跑了 ≥10 次划分给 mean ± std 吗？

**评估层**
- [ ] macro 指标指定了 `labels=` 完整标签空间吗？
- [ ] 主指标是 macro F1 / balanced accuracy，不是 accuracy？
- [ ] 比较模型用的是逐划分配对差吗？

**上线层**
- [ ] 窗口配置和模型一起持久化了吗？
- [ ] 训练/预测一致性六项核对过了吗？
