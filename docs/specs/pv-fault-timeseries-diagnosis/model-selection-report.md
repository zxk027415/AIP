> **术语澄清（阅读全文前请先看）**：本项目的任务是**故障诊断（Diagnosis）**——输入一段
> **已经发生**的时序，输出它属于 13 类故障中的哪一类，时间方向是**回看**。
>
> 本报告中出现的「末 N 天」「时间隔离」「未见日期」**一律指评估协议**，即 test 集使用训练时未出现过、
> 时间上更靠后的日期，**不是** Prognosis / 故障预测（判断设备将来会不会坏、剩余寿命）——
> 后者本项目**没有做**，当前标签也不支持（99.79% 标注点来自天级批量导入，无故障起始时刻）。
>
> 诊断任务之所以也要隔离日期：模型上线后 `predict()` 的输入永远来自它没见过的新的一天。
> 若 train/test 共享日期，模型可利用当天全站共享的气象条件（某时刻云层导致全站曲线同时下凹）
> 抄近道，而该捷径在线上不存在，分数因此虚高。隔离日期是为了让 test 的「天」对模型陌生。

### 阶段 2：数据正确性排查 — 发现 3 个 bug

#### Bug 1：跨支路混合

数据真正的时序主键是 `(site_id, device_id, branch_id)`，但切分器只按 `device_id` 分组。

| 事实 | 数据 |
|---|---|
| `device_id` 唯一值 | 1,642 |
| `(site_id, device_id, branch_id)` 唯一值 | **2,226** |
| 有多支路的设备 | 250 台（15.2%），最多 16 条支路 |
| `(device_id, time)` 重复行 | **86,124** |
| `(site,device,branch,time)` 重复行 | **0** ← 证明这才是主键 |

15.2% 的设备把 2~16 条不同支路的时序交错按时间排序后切窗，
样本在不同物理序列间来回跳变。

#### Bug 2：merge 笛卡尔积

`transform()` 内 `merge(point_labels, on="time")` 在时间戳跨支路重复时产生笛卡尔积：
2 支路 → 4 行/时间戳，16 支路 → 256 行。

| | 窗口数 |
|---|---|
| 修复前 | 19,050（虚增 2.8 倍） |
| 修复后 | **6,852** |
| 理论值（按主键，未计纯度过滤） | 7,353 |

#### Bug 3：sample_id 撞车（修前两个 bug 时引入）

`sample_id = f"tsc-{series_id[:16]}-{start}"`，而 `series_id` 形如
`site|device|branch`，截前 16 字符正好只剩 `site_id` → 同站点所有设备撞 id。
`load_and_split_all_devices` 按 `sample_id` 去重，会**静默丢窗口**。改为 blake2b 短哈希。

**修复产物**：`SamplerConfig.series_keys` + `resolve_series_keys()`；
单序列时间戳去重兜底 + 告警；8 个回归测试（支路不混合、无笛卡尔放大、
sample_id 唯一、主键解析三场景等）。

### 阶段 4：数据穿越严格审计

leader 要求排查是否存在数据穿越。逐项核查结果：

#### 已排除的泄漏假设

| 假设 | 检验方式 | 结果 |
|---|---|---|
| 标签由 `value`/`i_cal` 阈值推导（等于把答案喂给模型） | 查工作流定义 | **排除**。源数据无 label，标签由独立表按天对齐贴回，两者是原始测量值 |
| 模型靠「认日期」作答（train/test 共享全部日期） | 仅按日期查表预测 | **排除**。Acc=0.6924 / F1=0.3062，远低于模型 |
| 同上，按 (站点,日期) 查表 | 同上 | **排除**。Acc=0.7094 / F1=0.4229 |

#### 已确认并修复的问题

| 问题 | 严重度 | 详情 | 处理 |
|---|---|---|---|
| **指标口径错误** | 高 | `f1_score(average="macro")` 未指定 `labels=`，sklearn 只在 test 出现的类上平均，缺席的稀有类被静默排除。同一次预测：默认口径 0.8841，全 12 类 **0.7367**，差 **0.147** | 所有 macro 指标固定 `labels=完整标签空间` |
| **退化窗口泄漏** | 中 | 4.42% 窗口是常数序列（多为夜间全零），302/303 属同一类。不同设备的全零窗口**内容完全相同** → train/test 出现 **46 个字节级重复窗口**（占 test 3.73%） | 新增 `min_std` 过滤，设 1e-6 后重复窗口 **46 → 0** |
| **accuracy 被不平衡高估** | 高（易误导） | 多数类基线 accuracy 就有 **0.4665**（label 1 占 test 46.6%，label 1+11 约 68%） | 改用 macro F1 + balanced accuracy 作主指标，不再汇报 accuracy |

#### 无法用主数据集解决的结构性限制

| 限制 | 数据 |
|---|---|
| 日期极度稀疏 | 全数据集只有 **35 个日期**，散落 10 个不连续簇，密度 0.052 |
| 无法时间切分 | 按时间切后 test 只剩 10 个窗口 2 个类 |
| 标签**存量** 99.96% 是天级 | `(site,device,branch,date)` 内 label 唯一比例 **99.96%**（查 `point_labels` 原表确认）。系统支持子天 `human_range`，但存量仅 2 条操作 / 293 点 |
| 有效样本远小于窗口数 | 4,457 个独立 device-day 单元 → 6,852 窗口 = **1.54x 重叠虚增** |

#### ★ 一个正面验证：模型确实在用时序形态

**时间打乱消融**——把每个窗口内 288 个点随机重排：

| | macro F1 | Accuracy |
|---|---|---|
| 正常顺序 | 0.7283 | 0.9490 |
| **随机打乱** | **0.4122** | 0.7863 |

破坏时间顺序导致 F1 崩掉 0.32。这是反驳「结果全靠泄漏 / 任务本身平凡」的最强证据，
也直接支撑了本 spec「时序形态有价值」这个立项前提。

### 阶段 6：找到能做时间切分的数据块

主数据集做不了时间切分（35 个散落日期）。扫描全部数据源后找到替代：

| 数据源 | 最长连续段 | 设备 | 类别 | 可用 |
|---|---|---|---|---|
| **`dataset_combined.parquet`** | **7 天（密度 1.0）** | 241 | 6 | ✅ 最佳 |
| `train_ori/xiangyin` | 9 天（密度 1.0） | 807 | 10 | ❌ 切窗后 90% 单一类 |
| `train_ori/yuncheng` | 9 天 | 313 | 7 | ❌ 同上 |
| 主数据集 | 9 天 / 共 35 天 10 段 | 1642 | 13 | ❌ 密度 0.052 |

**三口径对比（dataset_combined，单次划分）**：

| 口径 | MiniRocket | MultiRocket | 聚合特征基线 |
|---|---|---|---|
| A 按设备划分（同期跨设备） | 0.7623 | 0.7303 | 0.7747 |
| B 按日期划分（末 3 天，训练未见） | 0.7147 | 0.7542 | 0.5993 |
| **C 双隔离（末 3 天未见日期 × 未见 30% 设备）** | 0.6940 | **0.7635** | **0.4316** |

**★ 关键发现：TSC 相对聚合特征的优势只在严格口径下才显现。**
聚合特征基线在口径 A 是 0.7747（还略高于 TSC），到口径 C 崩到 0.4316；
MultiRocket 在口径 C 仍有 0.7635。差距从 **−0.04 变成 +0.33**。

原因是聚合统计特征在「同期同设备群」上过拟合了设备/时段特有的幅值水平；
时序模型对未见设备 + 未见日期的泛化明显更好。**用宽松口径会得出「聚合特征更好」的错误结论。**

### 阶段 7：方差量化 — 单次划分全部不可信

**触发**：同一协议（口径C / window=288 / stride=72）两次运行得到 0.7635 与 0.6495，差 0.11。

固定时间切点，对「保留哪 30% 设备」跑 **10 个种子**（10/10 隔离自检通过）：

| 模型 | macro F1 | balanced acc | accuracy |
|---|---|---|---|
| **MultiRocket** | **0.6315 ± 0.0750** [0.517, 0.719] | 0.7747 ± 0.1181 | 0.8881 ± 0.0420 |
| MiniRocket | 0.5534 ± 0.0789 | 0.7348 ± 0.1021 | 0.8501 ± 0.0464 |
| 聚合特征基线 | 0.5222 ± 0.0520 | 0.6335 ± 0.0879 | 0.8561 ± 0.0389 |

**std = 0.075，极差 0.20。** 至此确认：**所有单次划分数字均不可对外引用。**

**配对差 MultiRocket − 聚合特征 = +0.1094 ± 0.0669，9/10 划分胜出。**
这是 TSC 路线价值最可靠的量化——不是某次幸运划分看到的 +0.33，而是稳定可辩护的 +0.11。

### 阶段 8：窗口长度敏感性 — 缩短窗口有害

窗口数从 6,535 涨到 19,597、可用设备 1095→1576、类别 12→13，表面全面变好，故实测：

| window/stride | 窗口数 | macro F1 | 相对基线 | 隔离自检 |
|---|---|---|---|---|
| **288/72** | 2,918 | **0.6495** | 基线 | OK |
| 288/36 | 5,613 | 0.5730 | −0.077 | OK |
| 144/36 | 6,902 | 0.5164 | −0.133 | OK |
| 144/18 | 13,612 | 0.5256 | −0.124 | OK |
| 96/24 | 9,978 | 0.5217 | −0.128 | **BAD** |
| 72/18 | 12,469 | 0.4892 | −0.160 | **BAD** |

窗口数翻 4.7 倍，精度掉 0.12。**原因**：当前标签存量 99.96% 是天级粒度，整天窗口
（288 点）恰好匹配；更短窗口只看到一天的一部分，判不出当天标签。且窗口越短越容易在
不同设备间字节级相同，引入新泄漏（96/72 隔离自检直接 BAD）。

该结论绑定当前标签存量，不是架构结论——子天 `human_range` 标签若积累起来需重评。

**结论：保持 288/72。**

## 三、最终选型

| 项 | 值 |
|---|---|
| **模型** | **MultiRocket**（`aeon.classification.convolution_based.MultiRocketClassifier`） |
| window_length | 288（= 1 天，5 分钟采样） |
| stride | 72（= 6 小时，75% 重叠） |
| channels | `[value, i_cal]` |
| 预处理 | `per_sample_zscore` |
| min_std | 1e-6（剔除常数/全零退化窗口） |
| 序列主键 | `(site_id, device_id, branch_id)` |
| **macro F1（全类）** | **0.6162 ± 0.0710** |
| balanced accuracy | 0.7650 ± 0.1053 |
| 相对聚合特征基线增益 | **+0.1094 ± 0.0669**（9/10 划分胜出） |
| 训练耗时 | 约 20~150 秒（视样本量），无 GPU 依赖 |

### 选型理由

1. **精度第一**，且对 Tier 2/3 全部深度模型有 0.11~0.19 的配对差优势（3 个模型 0/10 落败）。
2. **对 MiniRocket 有 +0.0782 ± 0.0665 优势**，9/10 划分胜出。
3. **无 GPU 依赖**，训练秒级到分钟级，适合频繁重训的生产场景。
4. **相对聚合特征（RF 路线的特征形态）有 +0.11 稳定增益**，且该优势只在严格口径下显现，
   说明时序模型对未见设备 + 未见日期的泛化更好。

### 关于 v4 数字的小幅波动

四次严格口径运行中 MultiRocket 分别得到 0.6315 / 0.6031 / 0.6176 / 0.6162。
原因是 `get_model()` 未给 aeon 模型传 `random_state`，
故报告的 std **同时包含「划分差异」与「模型内部随机性」**。
这反映真实部署波动，属可接受范围；若需单独量化划分方差，应固定模型随机种子重测。

| ROCKET | 严格口径下垫底（0.4680），配对差 −0.0569，仅 2/10 胜出。v2 的第一名是宽松口径假象 |
| MiniRocket | 配对差 −0.0782（9/10 输给 MultiRocket）。优点是快 3 倍，若极端在意训练时长可作备选 |
| ROCKET + RandomForest | 0.5105，配对差 −0.0145，4/10。把 ROCKET 特征交给 RF 不如默认 Ridge |
| ResNet-1D | 0.4256，**0/10**，配对差 −0.1906 |
| InceptionTime（ensemble） | 0.4967，**0/10**，配对差 −0.1195。集成未带来收益（与单模型差 0.013，在 std 内） |
| Inception 单模型 | 0.5097，2/10，配对差 −0.1065 |
| CNN-LSTM | 0.4242，**0/10**，配对差 −0.1920 |
| CNN-BiLSTM-Attention | 0.4546，1/10，配对差 −0.1616 |
| 缩短窗口（144 / 96 / 72） | 实测 −0.077 ~ −0.160，且短窗口引入字节级重复泄漏 |

### 关于「深度模型为何全部落败」的因果说明

v1 的解释是「462 个训练窗口太少」，该**推理链**已作废（462 是当时取样失误造成的）。
但用干净数据 + 严格口径 + `epochs=200` + GPU **独立重验后结论相同**。

修正后的解释：**不是取样问题，而是可用数据本身就只有这么多**——
严格口径下训练集约 870 窗口，对深度网络仍然过小。ROCKET 家族靠随机卷积核 +
线性分类器，小样本下泛化更稳。

**推论**：若将来窗口量增长到数万级，深度模型值得重新评估；当前数据规模下可关闭该线。

## 七、方法论沉淀（对后续项目同样适用）

1. **精度过高先怀疑度量，不要先高兴**。本次 0.9579 → 0.6162 全部来自度量与数据修正，
   模型本身没变。
2. **序列主键必须与业务实体严格对应**。`device_id` 看似够用，实际 15.2% 的设备有多支路。
3. **macro 指标必须显式指定 `labels=` 完整标签空间**，否则稀有类缺席会静默抬高分数（本次 0.147）。
4. **类别不平衡场景不要用 accuracy 汇报**。本任务多数类基线 accuracy 已达 0.4665。
5. **单次划分不可引用**。本次 std = 0.075、极差 0.20，两次同协议运行差 0.11。
6. **比较两个模型要用逐划分配对差**，不是比各自的 mean ± std。
7. **评估口径必须匹配生产场景**。宽松口径下聚合特征"赢"了 TSC，严格口径下差 0.33，
   结论完全相反。
8. **每个 bug 都要留回归测试**，否则修完还会回来。
9. **样本数增长 ≠ 信息量增长**。缩短窗口使样本数翻 4.7 倍，精度反降 0.12。
10. **跨环境复现是廉价而高价值的验证**。本次 Windows CPU 与 Linux GPU 差 0.0014，
    一次性排除了整类环境相关隐患。
