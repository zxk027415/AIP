# seq_annotation 第四路径接入仍存在生产隔离与自然日契约缺口

本次改动把 `seq_annotation` — 序列标注建模路径接入累计快照、专用训练工件、scheduler 逐点预测、人工审核和路径切换控制面，并采用“先登记实验模型、人工切换后才进入生产”的策略。工件采用 `metadata.json` — 模型元数据与 `model.pt` — 模型权重组成的目录契约，逐点详情完整保存在批次 JSON，数据库预测记录只保存分段摘要和引用。聚焦测试、Python 编译和前端构建均通过，但关键反例没有被现有测试覆盖。Watch for: **confirmed** 未 Promote 的首个实验模型会被兼容回退重新暴露为生产引用；**confirmed** 稀疏业务标签会产生未注册类别；**confirmed** 半天数据可被标记为“全天 288 点”并推进生产游标；**confirmed** 异步训练在运营卡片中没有持续状态或失败反馈。

**Verdict**: NEEDS_CHANGES

## High-level view

实验登记与生产指针的主写入分支已经分开，但读侧仍保留“没有生产指针就返回最近完成模型”的旧兼容逻辑。首个完成模型如果恰好是 seq 实验模型，scheduler 会取得它的引用，同时仍读取到 `legacy_day` — 旧天级生产路径，破坏“不自动 Promote”的核心隔离。

训练工件把业务标签 ID 直接当作神经网络类别下标，输出维度取最大标签加一。光伏标签空间存在跳号时，模型会包含从未训练、也未登记的中间输出神经元，而预测端对全部 logits 直接 argmax，可能产生注册表中不存在的标签。

“全天”资格目前来自 `seq_len` — 序列张量长度等于 288 和配置中的 `[0, 24]`，不来自实际 5 分钟槽位覆盖。训练和预测均接受 144 点并在尾部补零，也不重建固定自然日网格；scheduler 又把任何早于今天的日期当作完整日，因此半日、缺点或非 5 分钟序列都可能以全天模型口径训练、预测和 Promote。

scheduler 的逐设备水位使用最后一个已处理时间点，查询条件是严格晚于该水位。历史日部分数据被提前处理后，同日更早的晚到点将永久落在水位之前；批次和审核会话写入失败时，已落库的预测记录也没有事务回滚，重试会形成重复记录。

运营前端只在启动 HTTP 请求期间显示 loading，随后既不轮询累计重训状态，也不展示后台失败。路径配置和对比接口错误还被转换为 `null`，页面会把读取失败呈现成“尚未训练/无结果”，无法区分真实空态与错误态。

## 实验登记被生产引用兼容回退绕过

**Confirmed.** `_execute_cumulative_retrain` 接收重训请求 ID 和 `slot` — 业务槽位，执行快照训练并把 seq 结果以 `promote_to_production=false` — 不晋升生产交给累计训练服务；该函数由手动/自动重训后台任务调用，输出完成请求和 publication 状态。这个写侧分支不会设置 `production_model_ref` — 当前生产模型引用（`backend-service/api/iterative_labeling.py:689-738`）。

读侧的 `CumulativeTrainingService.get_production_model_ref()` 输入当前槽位状态、输出 scheduler 使用的生产模型引用；当显式生产引用为空时，它无条件返回最近一条 completed 请求的 `model_ref` — 模型工件引用（`backend-service/services/iterative_labeling/cumulative_training.py:547-555`）。`_summarize_state()` 也执行同样回退，把最近完成请求展示为 production model（同文件 `1160-1164`）。因此在一个尚无 RF 生产模型的槽位中完成首次 seq 训练后，`get_modeling_paths()` 仍显示 `production_path=legacy_day` — 生产路径仍为旧天级，但 `get_production_model_ref()` 和累计状态会返回 seq 工件。scheduler 随后用 legacy `.pkl` 解析器查找该目录型引用并进入 `model_pending`，同时 API 已对外误报实验模型为生产模型。

现有 `test_seq_annotation_model_is_registered_without_automatic_promotion` 只断言 `get_modeling_paths()`，没有调用真正供 scheduler 使用的 `get_production_model_ref()` 或 `get_state()`。兼容回退需要排除显式 `promote_to_production=false` 的完成请求，并增加“没有既有生产模型”的回归用例。

## 稀疏业务标签会产生未登记预测类别

**Confirmed.** `SeqAnnotationTrainer.train()` 读取业务标签数组并以 `max(labels) + 1` 创建输出层（`backend-service/services/iterative_labeling/seq_annotation/trainer.py:68-69`）。例如训练数据只有 `[0, 4, 7]` 时，模型仍会生成 8 个 logits，其中类别 1、2、3、5、6 从未作为目标出现。

`SeqAnnotationPredictor._load()` 保存了 metadata 中的合法 `labels` — 业务标签 ID 列表，但只验证 `n_classes` — 输出类别维度能覆盖最大标签，没有构造 dense-index 映射或合法类别 mask（`backend-service/services/iterative_labeling/seq_annotation/predictor.py:76-83`）。`predict_device_day()` 对所有 logits 直接执行 softmax 和 argmax（同文件 `193-195`），因此未被监督的中间输出仍可能获胜，并作为 `predicted_label` — 天级兼容预测标签、逐点标签和分段标签进入数据库与审核批次。当前测试工件只使用连续 `[0, 1]`，没有覆盖 pv_fault 常见的跳号标签空间。

工件契约需要持久化 `class_index` — 模型连续类别下标到 `label_id` — 业务标签 ID 的映射，并在训练目标、评估和预测中双向转换；或者至少在 argmax 前屏蔽 metadata 合法标签之外的 logits。

## “全天 288 点”标志没有证明全天覆盖

**Confirmed.** 数据集构建器声明 `SEQ_LEN=288`，但 `MIN_POINTS=144`，质量门控也只要求有效行数达到 50%；不足 288 的序列随后在尾部补零（`backend-service/services/iterative_labeling/seq_annotation/dataset_builder.py:36-37, 334-341`）。它没有按自然日生成 288 个固定 5 分钟槽位、检查首尾覆盖、检测内部缺口或按时间插值；超过 288 行则直接截取前 288 行。

训练器仅用数组第二维等于 288 且 `daylight_hours` — 训练覆盖小时配置为 `[0, 24]` 计算 `trained_full_day=true` — 模型被认定为全天训练（`backend-service/services/iterative_labeling/seq_annotation/trainer.py:104-108`）。由 144 个上午观测加 144 个补零构成的样本也会产出可通过 `set_modeling_paths()` Promote 门控的“全天模型”。预测器同样接受 `seq_len * 0.5` 个点，按行排序后截断/补零，不验证 5 分钟槽位（`backend-service/services/iterative_labeling/seq_annotation/predictor.py:145-181`）。缺失 08:00 点会把后续所有点向前错位，而不是留在正确时间槽。

`trained_full_day` 被累计训练服务作为生产切换安全条件，scheduler 也据此允许夜间诊断。应把“输入张量长度”和“真实全天覆盖”拆成两个字段，只有固定网格覆盖达到约定阈值、夜间槽位真实参与训练时才写全天资格；训练与预测必须复用同一个按自然日 5 分钟重采样器。

## 自然日水位会漏掉晚到点并重复拆分同一天

**Confirmed.** `_run_seq_annotation_prediction_cycle()` 输入逐设备游标和未标注观测，按自然日调用预测器，输出批次、审核会话并更新 `DevicePredictionCursor` — 每设备预测时间水位表。它把所有 `date < cutoff.date()` 的行视作 completed，不检查 288 槽覆盖（`backend-service/services/scheduler/tasks/pv_fault_tasks.py:836-840`）；预测器接受半数点后，水位被更新为该日现有最大时间（同文件 `871-874, 933-950`）。

仓储 `query_unlabeled_by_point_labels()` 接收设备和时间边界，返回未被 point_labels 覆盖的观测；其下界使用 `TrainingSample.time > after_time`（`backend-service/services/db/repositories/pv_fault.py:321-371`）。可复现路径是：昨日先到 00:00–12:00 共 145 点，首次任务会预测并把水位推进到 12:00；随后补到的昨日 11:55 永远不会再查询。若后到的是 12:05–23:55，它们会在下一轮作为同一个自然日的第二段重新预测；不足 144 点时任务会停在旧水位反复重试，达到 144 点时则产生第二个同设备同日期审核单元。

自然日任务需要按“已封账日期/日期状态”推进，而不是按日内最大时间推进。至少应先固定网格检查完整度，成功后把设备水位推进到自然日结束边界，并为晚到数据定义显式重开/修订策略；当前“失败不推进、下次补”注释与严格时间水位行为不一致。

## 预测记录、批次和审核会话不是一个提交单元

**Confirmed.** seq scheduler 先逐条调用 `insert_prediction_record()`；该仓储函数接收一条预测字典、独立提交并返回数据库记录（`backend-service/services/scheduler/tasks/pv_fault_tasks.py:891-912`；`backend-service/services/db/repositories/pv_fault.py:169-194`）。之后 scheduler 才写批次 JSON、创建审核会话（scheduler 文件 `913-929`），最后更新设备游标。若批次文件写入、审核会话保存或游标 upsert 任一步失败，已提交的数据库记录不会回滚，水位也不会推进；下次任务会对同一输入再次插入预测记录。

数据库字段保持了紧凑策略，只写 `segment_predictions` — 连续预测段摘要和 `detail_ref` — 批次详情引用，完整 288 点详情放在批次 JSON；风险来自跨存储边界缺少幂等键/恢复协议。应以稳定的设备日键加模型版本建立唯一约束或幂等 upsert，并在批次状态中区分 prepared/committed，使重试复用已有批次。

## `segment_iou` 实际是逐点故障掩码 IoU

**Confirmed.** `SeqAnnotationTrainer._evaluate()` 输入模型、测试张量和合法标签，输出训练工件中的评估指标；它把所有测试序列展平，计算 `y != 0` 的逐点交并比，然后以 `segment_iou` — 名义上的分段 IoU 返回（`backend-service/services/iterative_labeling/seq_annotation/trainer.py:252-268`）。它没有提取连续段、匹配真值段与预测段，也没有边界容差，因此不能衡量分段边界质量。

该字段随后进入路径模型 metrics，前端以“分段 IoU”展示（`frontend-sevice/src/pages/accuracy-operations/PvFaultSplitModeOpsPanel.tsx:248-253`）。应将当前指标重命名为 `fault_mask_iou` — 故障点掩码 IoU，或实现真正的 segment-level 匹配后再保留现名；历史工件 metadata 需要按 schema version 区分语义。

## 288 点训练按钮没有后台生命周期状态

**Confirmed.** `ModelingPathCompareCard` 负责读取路径对比与生产路径配置，并启动 seq 实验训练。其“训练 288 点路径”调用一步式后台接口，但 `seqTraining` 只覆盖该 HTTP 请求，接口返回后立即在 `finally` 中恢复 false（`frontend-sevice/src/pages/accuracy-operations/PvFaultSplitModeOpsPanel.tsx:86-105`）。页面的 8 秒轮询只在 RF 路径对比 `compare.status === 'running'` 时开启（同文件 `63-68`），没有读取 `/cumulative-training/state` 的 `latest_retrain_request.progress` — 最近重训请求阶段与进度。因此数分钟的快照冻结和训练期间按钮重新可点，进度、失败原因和完成状态都不会自动出现；用户只能手工刷新，重复点击会得到后端 409。

同一组件把路径对比和路径配置读取异常都 `.catch(() => null)`（同文件 `51-57`）。配置接口失败时，seq 行会被构造成 `not_trained`，Promote 按钮以“需先完成训练”禁用，而不是展示加载错误；这会把网络/后端故障误判成真实空态。应复用部署页已有的累计重训轮询，按 queued/preparing_snapshot/running/completed/failed 展示状态，并把配置加载错误与“尚无模型”分开。
