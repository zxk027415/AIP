## High-level view

`insert_prediction_records()` — 输入一批预测记录字典，输出已提交的 ORM 记录 — 在同一个 `DBAdapter.get_sync_session()` 事务里完成校验、flush 和 commit，任一记录或 commit 失败都会回滚整批。批次文件先原子替换落盘，数据库记录随后保存批次引用，为审核失败后的恢复提供真源。

`_partition_seq_predictions_for_recovery()` — 输入当前模型、本轮有效预测和质量门控前的候选设备日，输出真正新增预测及待恢复 batch ID — 已从数据库行读取首次 batch，而不是用本轮集合重算旧批次。集合从 A 变为 A+B、A-B，或 A 被本轮质量门控排除时，命中 A 的任一数据库记录都会恢复 A 的完整 `predictions` — 首次预测结果、`dataset_version` — 首次来源数据路径和 `cursor_advance_times` — 首次设备游标时间；**[confirmed]** 恢复资格额外要求记录的 M1 等于当前 M2，导致模型切换时恢复链断开。

恢复审核在新批次写入之前执行，新批次审核又在游标 upsert 之前执行；任一步抛错都会跳过游标更新。`ReviewSessionService.create_session()` — 输入预测 batch 与待审核单元，输出可复用审核会话 — 按 batch 派生稳定 `review_id` — 审核会话 ID，因此重复恢复不会复制审核队列。

seq Promote 仍只有正式重训完成或显式路径切换两条入口：普通 `register_path_model()` — 登记路径候选模型的服务入口 — 拒绝 seq，`mark_retrain_request()` — 完成重训登记并按开关决定是否切生产 — 在 seq 自动 Promote 前校验完整生产契约，显式路径切换和 fallback 也重复校验。生产契约、调度预测详情和审核 overlay 对关键布尔使用真实 JSON boolean 判断，不接受字符串真值。

## 当前模型引用阻止旧模型 batch 恢复 [confirmed]

数据库提交后，`PredictionRecord.input_feature_json` — 预测记录输入上下文同时保存首次 `prediction_batch_id` 和首次 `model_ref` — 模型引用。重试分区时，代码先把任何命中的业务键加入 `existing_keys`，确保它不会进入新 batch；但只有 `existing_model_ref == model_ref` 时才把旧 batch 加入 `recovery_batch_ids`。恢复循环随后又用当前 `model_ref` 调用 `_load_seq_recovery_batch()` — 输入 batch ID 与期望模型引用、输出首次预测/来源/游标事实的加载器，该加载器会拒绝 batch 内保存的不同模型引用。

故障时序为：M1 写完 A 的数据库记录后，审核创建失败，游标保持原位；在下次调度前生产模型 Promote 为 M2；M2 对相同设备日重新推理后命中 M1 数据库记录。A 被 `existing_keys` 从 M2 新批次移除，又因模型不一致不进入恢复集合，最终走 `all_duplicate` 且不推进游标。后续每轮重复相同行为，M1 的首次审核无法补建。

恢复集合需要同时携带旧 batch ID 和旧 model ref，加载和审核均使用数据库保存的旧值；当前模型只应用于真正新增单元 B。应增加“数据库提交后审核失败，再 Promote M2”的回归测试。

## API 文件的生成代码边界失配 [confirmed]

`backend-service/api/iterative_labeling.py` — 迭代标注 HTTP 接口与重训编排文件 — 的 AI 标记都是当前差异新增。标记扫描确认：默认累计训练服务的大块标记内又开启手动重训标记；累计训练 API 大块内又开启 `manual-run` 和后台执行标记；训练候选大块内又开启 TSC 标记且外层到文件末尾仍未闭合。文件中还存在没有对应开始标记的结束标记。

这些标记不改变 Python 运行，但会让审计工具无法准确判断生成代码边界，违反本次明确要求的“不得嵌套、必须成对闭合”。应将大块拆成互不重叠的小块，或保留外层并删除其内部标记；修复后重新扫描，要求每个文件 peak=1、final=0 且无 orphan end。
